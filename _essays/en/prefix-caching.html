The Illustrated Prefix Caching

Open an Agent request log and you find something odd: the start of every turn is almost identical — the same system prompt, the same tool definitions, and the conversation history accumulated along the way. Every time, the model dutifully reads them from the beginning (Prefill), and the bill charges them as “new input” every time.

On the pricing page, cached input is 10–50 times cheaper than a cache miss. This essay answers: on what basis can the model say “I already read this”? How does it find the stretch it read last time, within milliseconds? And which ways of writing break the cache?

This is a follow-up to Illustrated KV Cache. That essay explained why K and V can be stored. This one explains continuing to use them across requests. Reading the KV Cache essay first makes this smoother. If you have not read it, that is fine: the parts you need are repeated here.

Every agent turn repeats the same work

Let us look from the outside first. In an Agent session, the user asks one thing, the model answers, and the next request has to send the whole conversation again. The figure below is three turns. Each block is one stretch of content, and the number under a block is the token count (illustrative).

Three turns. Click the switch above to toggle “without / with prefix caching”, and look at “how many tokens were computed” on the right. Green = cache hit, pink = needs Prefill.

Note: without a cache, the three turns must Prefill 3,200 + 3,700 + 4,200 = 11,100 tokens in total. With a cache, only 3,200 + 500 + 500 = 4,200. The newly added content is only about 500 tokens. The rest is recomputing work that was already done. As the conversation grows, this gap keeps getting wider.

Prefix caching does something plain: keep the K and V computed by the last Prefill. If the next request starts the same way, use them directly, and compute only the new part.

Why it has to be a “prefix”

Why does the cache accept a match only at the start, and not “a matching stretch in the middle is fine too”? Because K and V depend not only on the word itself, but also on every word to its left.

Why can K and V be reused only as a prefix? (derived from the mechanism, not from a vendor document)

Criterion: a word's K and V at one layer are determined by “this word and every word to its left”.

  • The decoder's self-attention is masked: word $i$ can see only words 1 through $i$, and cannot see anything to the right.
  • In layer 1, the output of word $i$ depends only on $t_1,\dots,t_i$. The input of layer 2 is the output of layer 1, so in layer 2 it still depends only on $t_1,\dots,t_i$. Carry this down layer by layer, and every layer is the same.
  • So the K and V of word $i$ can be written $K_i, V_i = f(t_1,\dots,t_i)$: as long as these $i$ words (together with their positions) do not change, the K and V are identical, with nothing changed, and can be used directly.
  • The other way around: if word $j$ changes, then for every word from $j$ to the right, the “left” they depend on has changed, and their K and V are all invalid.

Click any word to change it: its K and V, and the K and V of every word to its right, all have to be recomputed (pink). The ones to the left can still be reused (green).

This rule decides everything that follows: how the cache matches, how you write the prompt, and why a single timestamp can destroy the hit rate.

Finding last turn's prefix in milliseconds: blocks and a hash chain (vLLM)

The most naive way is to compare the new request's tokens, one by one, with past requests. Too slow. This section is what the open-source engine vLLM does. The blocks come from its PagedAttention (Kwon et al., SOSP 2023). Matching a prefix automatically by hash is Automatic Prefix Caching, built by vLLM on top of that. It cuts the prompt into fixed-size blocks (a block; the typical value in vLLM is 16 tokens per block; the figure below puts only 3 in a block so it fits), then computes a hash for each block.

The key: each block's hash also folds in the previous block's hash (the vLLM docs put it this way: hash using the tokens in the block and the tokens before this block). So the hash of block $i$ stands for the whole prefix “from the start through this block”, not only this block's own content. Besides the tokens, the hash also carries extra information that “makes this block unique”, such as a LoRA ID, the hash of multimodal inputs, and a cache salt, so different things do not collide.

$$h_i = H\big(h_{i-1},\ \text{tokens of block } i\big),\qquad h_0 = \varnothing$$

Request A is already cached. Click a word in request B to change it: this block's hash changes, and the hashes of every later block change with it. Even if the later content is not changed by a single character, it is a MISS. Words in a trailing partial block do not enter the cache.

vLLM manages this with a “hash → block” hash table plus a free-block queue. Each block has a reference count. Only full blocks are cached. A cache lookup is a table lookup by hash: is B's $h_1$ in the table? Yes, cache hit. Is $h_2$? … up to the first one that is missing. After that there is no need to look further. This process is a few hash-table lookups, $O(\text{number of blocks})$, so it is on the order of milliseconds.

Why blocks, rather than caching per token?

Criterion: the tradeoff between management cost and reuse granularity.

  • vLLM chooses “block + hash table”: metadata (the hash, the reference count) is amortized to one copy per block, and a lookup is a hash-table query. SGLang takes another path: token granularity (one token per page) plus a prefix tree. Matching is finer, but you have to maintain a tree.
  • GPU memory is already paged by block (vLLM's PagedAttention). A cache block and a GPU-memory block line up naturally. Reuse does not copy. It only adds one more pointer to the same block.
  • The cost: tokens in a trailing partial block have no hash and are not cached. And the hit length is always a multiple of the block size.

Many requests in one prefix tree (SGLang)

A service receives thousands of requests at the same time. There is a lot of shared prefix between them: every user of the same product shares one system prompt. If each request stored its own copy, GPU memory would run out fast.

SGLang's approach is called RadixAttention (the SGLang paper, Section 3, Zheng et al., 2023): a prefix tree (radix tree) manages “token sequence → the corresponding KV”, and an edge is labeled with a token sequence. A shared prefix is stored once, as the “trunk”. The part that differs for each request is a “branch” that splits off. vLLM does not use a tree, but the effect is the same: a shared prefix has the same hash, points at the same blocks, and is stored only once.

Look at this tree with a small example. Three requests, one word per token:

A: You are helpful . Fix this bug
B: You are helpful . Summarize the doc
C: You are helpful . Fix this typo

Their opening You are helpful . is the same. The tree merges a run of tokens with no branch into one edge. Each edge stores the KV for that stretch of tokens:

root ──[You are helpful .]──○──[Fix this]──○──[bug]
                            │              └──[typo]
                            └──[Summarize the doc]

Click Replay or Next step: first the three requests, then an ordinary prefix tree with one node per token, then the compressed radix tree, and finally how a new request splits one edge in two.

The shared You are helpful . has only one copy of the KV, used by A, B, and C. That is “the trunk is stored once”. The parts that differ, bug, typo, and Summarize the doc, are branches that split off.

A cache lookup starts at the root and compares along the edges, segment by segment. The hit runs as far as the match goes. Given You are helpful . Fix this bug, all three edges match, and the whole path is a cache hit. Given You are helpful . Fix that, the first segment matches. On the second edge, Fix this, only Fix matches, and the tree splits that edge in two: Fix stays in the shared part, and this and that each become a branch. That is the difference between a radix tree and an ordinary trie (a prefix tree with one token per node): a long run with no branch is merged into one edge, and the edge is split only when there is a branch.

vLLM does not use a tree: each block has one hash, and the lookup is a hash table. The first few blocks of A, B, and C have the same content, so the same hash, so they find the same block, and it is stored only once. The only difference: SGLang finds the shared part from the structure of the tree, and vLLM finds the shared part because the hashes are the same.

So a prefix tree and a block hash do the same job. Both exist to find the longest common prefix already in the cache, and to store that common prefix only once. Only the method differs:

Prefix tree (SGLang)Block hash (vLLM)
How it recognizes “this is the same prefix”Walk down the tree from the root, comparing tokens segment by segmentCompute each block's hash, and look it up in the hash table
StructureA tree. Edges store the token sequence and the corresponding KVA “hash → block” table, not a tree
GranularityEach tokenEach block (for example 16 tokens)
What makes a common prefix stored only onceThey follow the same edge in the treeThey compute the same hash and find the same block
EvictionEvict the leaf unused the longest, firstEvict the block unused the longest in the free queue

A block hash can do the job of a prefix tree, because each block's hash carries the previous block's hash: “the same hash” means “everything from the start through this block is the same”. That itself is a prefix relationship. The hash chain implies a tree. It is just not stored as a tree structure.

The real difference is in two places: match precision (the tree matches per token, so the hit length can be any number of tokens; vLLM caches only full blocks, so the hit length is a multiple of the block size, and a trailing partial block has to be recomputed) and implementation cost (a hash-table lookup is simple; a tree is finer, but splitting an edge means editing the structure). For someone using it, the effect is the same: a matching start is a cache hit, a different start is a cache miss. So “static first, dynamic last” holds for both.

100 users share one system prompt of 10,000 tokens, stored once as the trunk (green). Each person's question is a small branch (orange). Click “+ New request” to add a user, click a branch to mark it as just used, and click “Evict LRU leaf” to evict the branch nobody has used for the longest time.

What if GPU memory is full? Both evict by LRU (Least Recently Used), but the details differ:

  • SGLang: evict the leaf unused the longest first. After a leaf is deleted, its parent becomes the new leaf, and eviction continues in that order, so the shared trunk is touched last. Each node has a reference count. If a running request is using it (the count is not 0), it cannot be evicted. The cache and running requests share one GPU-memory pool.
  • vLLM: blocks nobody is using (reference count back to zero) enter the free queue. The head of the queue is the one unused the longest, and when GPU memory is tight they are evicted from the head. When a request ends, its blocks are returned to the tail of the queue in reverse order: a block further back depends on a longer prefix and is less likely to be reused by anyone else, so it is evicted first.

Either way, a popular trunk keeps being used by new requests, so it is the hardest to evict.

As for how OpenAI, Anthropic, and DeepSeek implement this internally, the official docs do not publish it. They only describe the external behavior (prefix matching, the whole stretch must match). The above is what the open-source engines do. Closed-source services most likely follow a similar idea (speculative). Do not take this as the implementation of those services.

Note step 4: the cache-miss “tail” still has to go through Prefill, but its attention computation reads the K and V of the 10,000 cached words, as if those K and V had just been computed. What the cache-hit part saves is recomputing K and V (and the forward computation of every layer before them), not the read done by the whole attention.

One more point: step 6 registers the new blocks into the cache, including the part generated this time. So in a multi-turn conversation, turn 2 can hit not only turn 1's prompt, but usually also turn 1's answer (by turn 2 it has already become input).

The only rule for a hit: identical from the first token on

Because of the hash chain, a cache hit is “the longest common prefix from the start”. Change a single character at the start and the hash chain breaks at the root. Even if ten thousand characters after that are completely the same, they are all a cache miss.

Each block is one stretch of content. Click a block in the bottom row to mean “this block changed”. Toggle “Timestamp first / last” and see, for the same amount of content, how much the hit rate differs when the timestamp sits at the start or at the end.

This is “prefix pollution”: writing something that changes at the very front of the prompt, such as the current time, a user ID, session state, or a random number. A few common traps follow:

What you writeResultFix
Write Current time: 2026-11-24 14:03:21 at the start of the system promptThe start of every request differs, and the whole cache is invalidPut the time in the last user message
Add or remove tool definitions in the middle of a conversationThe tool list is in the prefix. Change one tool and everything after it breaksKeep the tool list fixed, and control it with an “enabled or not” field
Unstable key order when serializing JSONThe same content, different bytes, a different hashFix the key order (sorted serialization)
“Compress and rewrite” history messagesA block in the middle changed, so everything after it is a cache missOnly append at the end. When you must compress, accept one invalidation
Put a static document after the user questionEach question pushes the document to a different positionDocument first, question last

Is picking tools dynamically (giving the model only some of the tools each turn) always faster? Not necessarily. It trades “compute a little less” for “the cache becomes invalid”:

Fixed full tool listDynamic tool selection
Tokens in the tool sectionMore (for example 5,000)Fewer (for example 1,000)
CacheThe tools and the system prompt can both hitOnce the tool list changes, the whole prefix is a cache miss from the start
Tokens to Prefill each turnOnly the new part, very fewThe whole prefix has to be recomputed (for example about 4,000 tokens)

An example: the system prompt plus tools is 8,000 tokens, of which the tools are 5,000. With a fixed tool list, after a cache hit each turn computes only the few hundred new tokens. With dynamic tool selection the tools are down to 1,000, but each turn has to Prefill the whole prefix of about 4,000 again. That is slower, and the input cost is higher. Sending fewer tools can win only when the tool list is very large (hundreds or thousands of them) and the cache would miss anyway (for example the gap between requests is so long that the cache has expired). (derived from the mechanism, not from a vendor document; the numbers are illustrative)

When you do not want the model to use some tools, do not delete them. “Cover” them. The approach in Lessons from Manus on context engineering (source: Manus's blog) is: do not change a single character of the tool list in the prompt. The prefix stays the same, and the cache still hits. Restrict the model at the step where it generates the output. At each step the model scores every possible next token (logits). Push the scores for the tools it should not pick down extremely low, so the probability is near 0, and the model cannot pick them. An analogy: the menu still prints every dish, but when you order you cover the ones that cannot be ordered. Note: the logit_bias in the note in this library is illustrative code. The blog post never mentions logit_bias. It only says “mask the token logits directly”. How that is done is below. Whether a hosted API can do this depends on the interface. The Anthropic docs state that changing tool_choice invalidates the cache only for the messages part. tools and system still hit. So “restrict the choice with tool_choice” is much cheaper than “changing the tool list” (I have not checked the other vendors).

How Manus does it, specifically (from the blog section “Mask, Don't Remove”): it first explains why not to delete. Tool definitions sit at the very front of the context. Change them once and the cache for everything after them is invalid. Actions in the history still refer to the deleted tools, so the model gets confused and tends to produce format errors or invent actions. The approach has three parts:

  1. A state machine: the current state decides which tools this step is allowed to use. The blog's example: when the user has just sent a new message, you must reply at once, and you cannot call a tool first.
  2. Response prefill: before the model starts to speak, write the beginning of the reply for it. The model can only continue from there. Three levels in the Hermes format: Auto prefills only <|im_start|>assistant, and the model decides whether to call a tool; Required prefills up through <tool_call>, so it must call a tool, and any tool is allowed; Specified prefills up through <tool_call>{"name": "browser_, so it must call a tool, and it can only be one of those whose name starts with browser_.
  3. A shared prefix on tool names: browser tools all start with browser_, and command-line tools all start with shell_. Prefill one prefix, and the choice is limited to one group of tools.

Put together: the tool list always holds the same four, browser_open, browser_click, shell_ls, and shell_run, and never changes. When the current state is “browsing a web page”, prefill {"name": "browser_, and the model can only complete it as browser_open or browser_click. The two shell_ tools are still in the list, but they cannot be chosen at this step. Neither the tool list nor the system prompt changed, so the cache still hits. The blog does not give concrete code for the state machine or the masking. Whether prefill is available in each vendor's API, I have not checked.

How much you save: latency and cost

The cache-hit part no longer goes through Prefill, so it saves two things at once: time to first token (how long the user waits for the first token) and the input price.

Pick a prompt length, and drag the hit rate. Time is estimated as “Prefill 5,000 tokens per second”. Cost is estimated with cache-hit price = 1/10 of the cache-miss price. Both are illustrative values.

A worked example: a prompt of 32,000 tokens, with a 90% cache hit. The tokens to compute drop from 32,000 to 3,200, and time to first token drops from 6.4 seconds to 0.64 seconds. The input cost is $0.1 + 0.9 \times 0.1 = 0.19$ times the original, about 20% of the full price. At a 100% hit rate, neither latency nor cost drops to 0, because cache-hit blocks still pay a read fee, and the last few tokens always have to be computed.

One thing to note: Prefill compute is not strictly proportional to the token count (the attention part scales with the square of the length), so in a real long context the fraction of time saved is usually larger than in the figure. The figure uses only the simplest linear assumption. (derived from the mechanism, not from a vendor document)

What determines time to first token (TTFT, Time To First Token)? Roughly: TTFT ≈ queue wait + Prefill time of the cache-miss part + the first Decode step + network and tokenization

  • Number of cache-miss tokens: usually the largest term. Prefill time mostly grows with it. This is exactly why prefix caching can lower time to first token: the cache-hit part is not computed.
  • Queue wait: when the service is busy, a request has to wait to be scheduled first. Even a short prompt is slow.
  • Model size and hardware: a larger model, and fewer GPUs, make Prefill slower.
  • Where the cache is read from: GPU memory is the fastest. A cache that has spilled to SSD (such as DeepSeek) is a bit slower to read.
  • Network and tokenization: usually small.

This structure is derived from the mechanism, not from a vendor document. It is not a formula published by any vendor. The slider figure above uses only the simplest term (number of cache-miss tokens ÷ speed). (derived from the mechanism, not from a vendor document)

Costs and limits

  • It occupies GPU memory or disk. Cached KV is not free: it sits in GPU memory, and when GPU memory is tight it gets evicted by LRU, so “yesterday's cache is still here today” is not guaranteed. Some vendors (such as DeepSeek) spill KV out to distributed SSDs, trading for more capacity. Reading it is a bit slower than GPU memory.
  • It has a lifetime. A cache is kept only for a while. Claude's cache has two tiers, 5 minutes and 1 hour. OpenAI's pricing page marks two tiers, 30 minutes and 12 hours (all of the above are from the pricing pages of 2026-11-24; they change over time; go by the official pages). Each cache hit refreshes the timer.
  • Block granularity costs something. The hit length is a multiple of the block size, and content in a trailing partial block does not enter the cache. Some vendors also do not cache a prompt that is too short (for example under 1,024 tokens). The exact threshold is whatever the docs say.
  • Caches are isolated from each other. If different customers could hit each other's cache, they could infer someone else's prompt content from “whether the response was fast”. So vendors usually isolate caches by account / organization and do not share them across customers (see each vendor's docs for the exact scope). (derived from the mechanism, not from a vendor document)
  • A hit depends on routing. In a multi-machine deployment, a request should be routed, as far as possible, to the machine that holds the cache for that same prefix. Otherwise it is as if there were no cache. This is also why some services suggest sending the same session id. (derived from the mechanism, not from a vendor document) In the open-source engines, cached KV blocks live in each inference instance's own GPU memory, and instances do not share by default. The OpenAI docs state that, within the same organization and region, routing for a given model depends on load, the prefix hash, and prompt_cache_key. The cache is not reused across organizations or across regions, and prompt_cache_key “affects routing, does not pin a request to one machine, and does not guarantee a hit”. The cache is not necessarily stored only in GPU memory: DeepSeek's docs state that it spills to disk. Where the other vendors store it, the official docs do not say.

Change the model, and the cache is invalid too. What the cache stores is K and V, computed with the model's own weights. Change the model (even a different version of the same model) and the weights differ. The same tokens produce completely different K and V, and the old cache means nothing to the new model. (derived from the mechanism, not from a vendor document) In the official docs: OpenAI lists model as a setting that affects the cached prefix. The original wording is “A different model can use different weights and caching behavior.” It also says that routing within the same organization and region is for a given model, but it does not write the sentence “changing the model is always a cache miss”. The part of the Anthropic docs I read does not discuss changing the model. It only writes that the minimum cache length varies by model, and that changing the thinking configuration, effort, and similar settings invalidates the cache. (For both vendors' docs, I read only the earlier part, word for word.) So switching models in the middle of one session (for example sending an easy question to a small model) makes the new model Prefill the whole prefix again, and can be slower and more expensive.

How to turn on caching in each API

The prefix rule is the same for all three. The only difference is who decides the cache breakpoint: with Anthropic you mark it, OpenAI is automatic by default and newer models can be marked by hand, and DeepSeek is fully automatic. Anthropic: two ways to write it. The first is the least work. Add one field at the top level of the request, and the system automatically places the breakpoint on the last cacheable block:

{
  "model": "claude-opus-5-5",
  "max_tokens": 1024,
  "cache_control": {"type": "ephemeral"},
  "system": "You are an AI assistant tasked with analyzing literary works...",
  "messages": [{"role": "user", "content": "Analyze the major themes."}]
}

The second is to mark the breakpoint yourself on a content block, choosing which block the cache runs through (the official example: the system prompt is split into two blocks, and the long-document block is the one marked):

"system": [
  {"type": "text", "text": "You are an AI assistant tasked with analyzing legal documents."},
  {"type": "text", "text": "Here is the full text of a complex legal agreement: [...]",
   "cache_control": {"type": "ephemeral"}}
]

What does “breakpoint” mean? It is a mark you insert in the prompt that says “cache up to here”: from the start, up to and including the block marked with cache_control, everything goes into the cache. What comes after that block does not. For example, if the request is, in order, tools, the system prompt, a long document, and the user question, marking the breakpoint on the “long document” block caches the first three blocks together. The user question, which differs every time, sits after the breakpoint. It is not cached, and it does not invalidate the cache in front of it. One cache_control at the top level is “marked automatically”: the system places the breakpoint on the last cacheable block. Writing it directly on one block is “marked by you”: you decide which block the cache runs through. The official limit is at most 4 breakpoints per request, and each breakpoint looks back at most 20 blocks. My guess at what several breakpoints are for is to place them at the boundaries between different “rates of change” (the tool list almost never changes, the system prompt changes now and then, the conversation history grows every turn), so that when one layer changes, the more stable cache in front of it can still hit. The official docs do not put it this way.

For a 1-hour cache, write it as "cache_control": {"type": "ephemeral", "ttl": "1h"}. The two ways of writing it can be used together.

cache_control means “this can be cached”. {"type": "ephemeral"} is the type of the cache. ephemeral means “short-lived, temporary”. The official docs write that it is currently the only supported type, with a default lifetime of 5 minutes, which is why the same phrase is written every time. Placed at the top level, it tells the system to put the breakpoint on the last cacheable block automatically. Placed on one block, it means “cache up to this block (including this block)”.

Anthropic's cached-prefix order is fixed as tools → system → messages. “A change at one layer invalidates that layer and every layer after it.” A few rules the official docs state explicitly:

  • Change the tool definitions: tools, system, and messages all become invalid.
  • Change tool_choice, or add or remove images at any position: messages become invalid.
  • A hit requires “a 100% match”, including all text and images, up through the block where the breakpoint is marked.
  • At most 4 breakpoints per request. Each breakpoint looks back at most 20 blocks, looking for a cache it can hit.
  • Below the minimum length, it is not cached even if marked, and it does not report an error. You only know by looking at the numbers in usage.

These line up with the “prefix pollution” above: Anthropic wrote “tools go first, and changing a tool breaks everything after it” into the docs.

OpenAI: automatic by default, with a manual option added on newer models. Older models cache automatically once the prefix is long enough. The official suggestion is to send a stable prompt_cache_key on requests that share the same prefix, to help route them to the same machine (it affects routing; it does not guarantee a hit). On GPT-5.6 and later, inside prompt_cache_options you can choose implicit (automatic; the breakpoint goes at the end of the last cacheable message) or explicit (you mark prompt_cache_breakpoint on a content block yourself), and use ttl to choose 30m or 12h. The writing on the official page is roughly as follows:

{
  "model": "gpt-6.2-sol",
  "prompt_cache_key": "support:customer_123",
  "prompt_cache_options": { "mode": "explicit", "ttl": "12h" },
  "input": [
    { "role": "developer", "content": [
      { "type": "input_text", "text": "Shared instructions...",
        "prompt_cache_breakpoint": { "mode": "explicit" } } ] },
    { "role": "user", "content": "The user's question..." }
  ]
}

This example is several separate snippets from the official page that I joined together. The field names all come from the official page, but the official page does not give a complete merged example. The "role": "developer" in the example is an OpenAI role, not a typo: the official text guide states that a developer message is instructions given by the application developer, with priority above user. The role values of the Responses API are user, assistant, system, and developer. Both developer and system rank above user. I did not find a document saying that developer replaced system. The official caching page also writes: to make reusable instructions eligible for the cache, put them at the start of input, in a developer message. Also, GPT-6.2 and later place the top-level instructions after input. That part is billed at the uncached price, so do not put static content you want cached there.

DeepSeek: add nothing. The official wording is that it is on by default for all users, and no code change is needed. Each request leaves one cache-prefix unit at “the end of the user input” and one at “the end of the model output”. It also leaves units at a detected common prefix and at fixed token intervals. A later request hits only if it matches in full some prefix unit, and the prefix has to have already been written into the disk cache. So the long-document example in the docs is that the first two requests both miss, and only the third one hits. The official docs also say explicitly that it is “best effort”, and do not guarantee a 100% hit.

The breakpoint principle the three share

Criterion: put the breakpoint at the boundary between “static” and “dynamic”.

  • Anthropic: mark the breakpoint on the last static block (after the system prompt, the tools, and the fixed documents), or use the top-level field and let the system place it on the last block automatically.
  • OpenAI: keep prompt_cache_key stable for the same kind of request. When using explicit, mark the breakpoint at the end of the static content.
  • DeepSeek: there is no breakpoint you can mark, so you can only rely on the prompt itself “staying the same at the front”.
  • Whichever vendor: after you ship, look at the hit numbers. Do not only trust “I wrote it right”.

A practical checklist

  1. Put static content first and dynamic content last. The system prompt, the tool definitions, and fixed documents go first. The user's question, the timestamp, and the session ID go last.
  2. Do not write the time, a user ID, or state at the start of the prompt. This is the most common prefix pollution.
  3. Do not add or remove tools, or change tool order, in the middle of a conversation.
  4. Only append to history. Do not rewrite it. If you compress the history, accept the cache invalidation of that one compression, then keep appending after that.
  5. Look at the hit count, then optimize. Look at the cache-hit token count in the API response (on DeepSeek that is prompt_cache_hit_tokens). Only when the number rises steadily are you actually getting the cache.
  6. The mechanism differs by vendor (pricing pages of 2026-11-24). Claude needs cache_control added on the request (you can add a single top-level field, and the system manages the breakpoints). A 5-minute cache write is 1.25× the input price, a 1-hour write is 2×, and a cache-hit read is 0.05–0.1×. OpenAI's pricing page lists a cache-write price on its own line (Sol as the example: 1.25× for 30 minutes, 2.5× for 12 hours). DeepSeek recognizes it automatically. No code change.

Explained for a 10-year-old

  1. Every day at school, the teacher starts by saying the same opening: “Hello, class. Today we will learn…”. Copying it from scratch, one character at a time, every time, is tiring.
  2. The smart way: copy it on the first day, and keep it. The next day, if the teacher's opening is the same, you just pull out yesterday's notes.
  3. But if the teacher's first character changes, you cannot use the notes directly, because every later sentence continues from the sentence before it.
  4. The notebook is big, and it still runs out of room. Then you tear out the pages you have not opened for the longest time, to make room for the new ones.
  5. So to save effort, the teacher (that is, the prompt you write) should put the words that will not change first, and the words that will change last.
  6. Each page of notes is not stored one character at a time either. It is a dozen or so characters per page. The page number is computed from the previous page's number, so you find it as soon as you flip.

Recap

  • Why it can only be a prefix: a word's K and V depend on the word itself and on every word to its left, so the whole stretch can be reused only when it is identical, character by character, from the first word.
  • How to find it: vLLM splits the prompt into blocks (typically 16 tokens per block). Each block's hash includes the previous block's hash, forming a hash chain, and a table lookup finds the longest cache-hit prefix. SGLang does prefix matching on a prefix tree.
  • How to store it: both approaches store a common prefix only once. When GPU memory is tight, both evict by LRU (vLLM from the head of the free queue, SGLang from the leaves).
  • How to use it: a cache-hit block does not go through Prefill. Only the cache-miss tail is computed. That saves time to first token, and it saves the input cost.
  • How to write the prompt: static first, dynamic last, only append to history, and do not change the tool list.
  • The boundaries: it has a lifetime, the tail block is not cached, it is isolated by account, and multiple machines need routing.
