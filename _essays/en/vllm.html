The Illustrated vLLM

Put the same model on the same GPU and swap the inference engine, and throughput can differ by 2–4× (measured in the vLLM paper at the same latency). These GPUs are often not using their full compute, while GPU memory (also called VRAM) is already “full”. This article answers: what fills GPU memory? How can vLLM fit several times as many requests into the same GPU memory?

There is only one clue: manage the KV Cache the way an operating system manages memory. We follow the method of “The Illustrated Transformer”: first look from the outside at how an inference server takes requests, then open its GPU memory, its scheduler, and the GPU, one step at a time.

This continues The Illustrated KV Cache and The Illustrated Prefix Caching: the first explains why K and V can be stored, the second explains how to reuse them across requests. This one explains how those K and V are actually laid out in GPU memory, and how an engine decides, at each step, who gets computed first.

Requests differ in length: short ones finish early, and long ones keep holding a slot

Let’s look from the outside first. An inference server is a “requests in, tokens out” interface. Requests arrive at different times. Some finish in 3 steps, some take 8. The figure below: batch size = 4 (at most 4 requests run in the same step), 6 requests (demo values). Three words are marked on the figure — each row on the left is one slot in the batch, and each column is one decode step (every request in the batch emits 1 token in that column), and the number on the colored bar is how many steps it generates.

Why do these three words show up? Because a GPU server has two facts that force you to think this way:

- Request: one question from one user. The server is not serving only you. Many people are asking at the same time, and each question is one request. - Decode step (also called an iteration): a large model emits only 1 token at a time. The next token cannot be computed until the previous one is out (autoregressive). So a 100-character answer runs the whole model from start to finish 100 times, and each run is one step. A step is the model’s smallest beat. - Batch size: at every step the GPU reads tens of GB of model weights once, and that cost is fixed. Taking a few more requests along costs almost no extra time, so computing them together is the best deal. But the number computed together has a cap (GPU memory cannot hold more people’s KV Cache), and that cap is the batch size. batch size = the number of requests the GPU serves in the same step (in vLLM this is the parameter max_num_seqs; in a real system it is also limited by KV Cache GPU memory, and is not a fixed value).

The figure uses 4 only so it fits on the page; a real server can be tens or hundreds. In one sentence: many requests wait in line, and each step lets only as many as the batch size advance, one cell each.

A–F in the figure are 6 requests from different users. The letters themselves mean nothing else: A is just saying hi, and the answer is short (3 steps); B is writing a long essay, and the answer is long (8 steps); C checks the weather (4 steps), D writes a summary (6 steps), E translates one sentence (4 steps), F replies “OK” (3 steps). The batch has only 4 slots at one time, so later arrivals have to wait. This figure only shows the problem: someone leaves early, someone keeps holding a slot. How a freed slot gets filled, and what the old method and the new method each do, is the next figure’s job.

But continuous batch processing has one prerequisite: when a new request fills in, GPU memory must have room for its KV Cache. Next, look at GPU memory.

How many requests run at once depends on the roughly 30% of GPU memory left for the KV cache

Take the paper’s example: a 13B-parameter model on one 40GB A100 keeps model weights in about 65% (26GB) of GPU memory, close to 30% for the KV Cache, and the rest is intermediate results. The weights are fixed. The only part that can be given to more requests is this 30%. So how many requests you can serve at once is almost exactly how many requests the KV Cache region can hold.

Top row: what GPU memory is made of. Bottom row: inside the KV Cache region, the share that actually holds a token’s K and V. The earlier systems compared in the paper average only 20.4%–38.2%. vLLM reaches 96.3%.

How big is one token’s KV? (computed for the paper’s OPT-13B)

Criterion: each token stores one K and one V for every layer.

  • OPT-13B has 40 layers, a hidden dimension of 5120, and each FP16 number is 2 bytes: 2×5120×40×2=819,200 bytes, about 0.8 MB / token (the paper writes 800 KB).
  • A request of at most 2048 tokens has at most 2048×0.8 MB≈1.6 GB of KV (the paper also gives 1.6GB).
  • A 12GB KV region, if every request reserves 2048 tokens, can hold only 7 requests. That is the problem in the next section.

The 40GB in the paper is a 2023 A100. Cards today have much more GPU memory. The table below is GPU memory per card for a few common GPUs (checked on 2026-11-24; numbers follow the vendor’s official page, and unofficial sources are marked):

Data-center cards have gone roughly from 80GB to 190–290GB. The larger the GPU memory, the larger the region left for the KV Cache after the model weights, and the more requests you can serve at once. But models are getting larger too, so the question “how much does the KV Cache take” has not gone away. The numbers have just moved to a larger scale.

On the API, max_tokens (also called max_completion_tokens) only limits, for this call, how many more tokens may be generated, and does not count the prompt. The 2048 above is the cap for the whole sequence: the prompt plus what still has to be generated. What the prompt already used, plus max_tokens, cannot exceed the model’s context. Static reservation still occupies KV by this whole-sequence cap. vLLM’s SamplingParams.max_tokens is also only “how many more to generate at most.”

Reserving the maximum length leaves only 20%–38% of KV GPU memory actually storing tokens

The previous section was this: when a slot in the batch frees, fill it immediately. But for this batch, how many slots it can have in total (the batch size), is set by how many requests’ KV Cache the GPU memory can hold. The old method wastes most of it right here and pushes the batch size very low. The two levels each handle one thing, and you have to solve both together for it to work:

What it managesProblem with the old methodNew method
SchedulingWhat to do when a slot in the batch is emptyLeave it empty and wait for the slowest requestFill a request in at every step (continuous batch processing)
GPU memoryHow many slots the batch can have at mostReserve the maximum length, waste GPU memory, and the batch size stays lowPaging allocates on demand, so the batch size can grow

Continuous batch processing without paging: the batch wants to fill a request in, but may fail because GPU memory is full of reservations. Paging without continuous batch processing: when a slot frees, you still wait for the whole batch to finish before filling it.

When a request comes in, the system does not know how long it will finally generate. The safest method is: first, for the maximum length (say 2048), carve out one contiguous region in GPU memory. This creates three kinds of waste (the paper’s categories):

WasteWhat it isWhy it happens
ReservationSlots kept for future tokens that are not used yetThis request is still generating, so other requests cannot use this region
Internal fragmentation2048 was reserved, only 200 was actually generated, and the remaining 1848 is never usedThe output length is not known in advance
External fragmentationFree space is enough in total, but it is cut into small pieces that cannot form one contiguous regionEvery request needs one contiguous region

Add these three up, and in the old systems only 20.4%–38.2% of KV GPU memory actually holds tokens (the previous figure). The root is the “contiguous” requirement: because every request needs one contiguous address range, you have to reserve, and so you have to waste.

PagedAttention cuts the KV Cache into small blocks and allocates them on demand, so waste shrinks to the leftover of the last block

Start with one question: a request’s KV Cache grows one token at a time, and nobody knows how long it will end up. The old method asks for one large region all at once, and the previous section already showed how wasteful that is. Can we give only as much as is used?

An analogy: you need to take notes, but you do not know how many pages you will write.

  • Old method: buy a 2048-page notebook first, in case you fill it. You end up writing 6 pages. The rest sits unused, and nobody else can use it. The notebook also has to sit on the shelf as a whole book. If the shelf has no gap that big, it does not fit.
  • New method: use small sticky notes, 4 lines each. When one is full, take another. A note can be dropped into any empty spot in the drawer. They do not have to sit next to each other. You only need one catalog: “note 1 is in drawer 7, note 2 is in drawer 1…”.

Map this analogy onto the KV Cache and you get the four words below (they are also the words on the figure):

  • Block = one sticky note: fixed size, holding the K and V of a fixed number of tokens. vLLM stores 16 per block by default. The figure puts only 4 in a block so it fits.
  • Logical block = “note 1, note 2” as you see them: the request numbers them 0, 1, 2… in order, and to the request these blocks are contiguous.
  • Physical block = the real spot in the drawer: the real block in GPU memory, which can sit anywhere.
  • Block table = the catalog: it records “logical block number → physical block number.”

This is the same idea as “paging” in how an operating system manages memory (block ≈ page, block table ≈ page table), so it is called PagedAttention.

How to read the figure: the top two rows are the logical blocks as request A (blue) and request B (orange) see them. The bottom row is the 8 real physical blocks in GPU memory. The lines in between are the block table. Click Next step. There are 5 steps in all:

  1. A arrives: the prompt has 6 tokens, so it takes only 2 notes (logical blocks 0 and 1). The catalog records them at physical blocks 7 and 1.
  2. B arrives: it takes 2 notes, placed at 4 and 6. A’s and B’s blocks are interleaved in GPU memory, but each one looks contiguous.
  3. A generates 2 more tokens: they are written into empty slots of the last note. No new note is taken.
  4. A’s last block is full: only then does it take one more block (logical block 2 → physical block 3), and the catalog gains one more line.
  5. A finishes: its 3 blocks return to the free pool at once (dashed boxes), and the next request can use them immediately. B is unaffected.

Click Next step and watch one step at a time. The top two rows are the contiguous logical blocks the two requests “think they see.” The bottom row is the 8 real physical blocks in the GPU. The lines in between are the block table (blue = A, orange = B). Cells with an orange outline are tokens newly written in this step: A’s and B’s blocks are interleaved in GPU memory, but each looks contiguous.

That removes all three kinds of waste from the previous section: no reservation (take only as much as you use); internal fragmentation is only the unfilled cells in the last block (at most 15 tokens, not thousands); external fragmentation is gone (every block is the same size, any free block can go to any request, and you never get “enough space in total, but no single contiguous region”).

Why can attention run on “scattered” blocks? (derived from the mechanism, not from a vendor document)

Criterion: each past token’s score q·kj uses only its own K. Where the other tokens sit, and whether they are next to each other, does not matter.

  • First, a reminder of what attention does: the new token’s Query (q) is dotted with each past token’s Key (kj) to get the score sj=q·kj; softmax turns the scores into weights αj=esj∑lesl; finally a weighted sum over the Values o=∑jαjvj.
  • The first step q·kj is fine with scattering: each j is computed on its own. K can sit in any block. The kernel looks up the block table, finds that block, reads K, and can compute.
  • Only softmax needs the “whole” (it needs the sum of all the scores). The method: each block first computes its own two quantities, ∑es and ∑esv, then add the blocks together and divide. The result is exactly the same as computing it in one pass. (A real implementation also subtracts the maximum score to avoid overflow. That is the “online softmax” used by algorithms such as FlashAttention.)
  • A small example: 3 past tokens, scores 2, 1, and 3, and the matching v is 1, 2, and 3. Block X holds the first two: ∑es=7.39+2.72=10.11, ∑esv=7.39×1+2.72×2=12.83. Block Y holds the third: ∑es=20.09, ∑esv=20.09×3=60.26. Combined: (12.83+60.26)÷(10.11+20.09)≈2.42, the same as computing it without splitting into blocks.
  • So the PagedAttention GPU kernel does not require K and V to be contiguous: it looks up the block table and computes one block at a time. The cost is one extra table lookup and non-contiguous memory access, so the kernel has to be written specially (the paper calls it the PagedAttention kernel).

Store the same content once, and copy it only when it has to change

Paging also brings an unexpected benefit: several requests can point at the same physical block. Typical cases are parallel sampling (the same prompt, several candidate answers), beam search, and the prefix caching from the previous article. Their prompt K and V are identical, so there is no need to store several copies.

The hard part of sharing: whoever writes into a shared block affects the others. vLLM does what an operating system does. It keeps a reference count on each physical block, and checks before a write — if the count is greater than 1, copy-on-write first.

Click Next step. S1 writes first: block P1 is shared (ref=2), so it is copied to P2 and then written. When S2 writes, only S2 is still using P1 (ref=1), so S2 writes in place.

Prefix caching is an extension of the same mechanism: after a request finishes, physical blocks are not cleared at once. They stay in the pool under a “content hash.” If the start of the next request has the same hash, the block table points straight at those blocks, and nothing is recomputed. Details are in The Illustrated Prefix Caching.

The scheduler decides again at every step who runs, and frees space when there are not enough blocks

With blocks, we can say how the engine turns. In vLLM (V1) the engine core (EngineCore) does one thing: it calls step() over and over. Each step has three stages:

  1. Schedule: decide which requests run this step, and how many tokens each one computes.
  2. Forward: the GPU runs the model once and samples the next token.
  3. Postprocess: append the new token to the request, and check whether it has finished (EOS, a length limit, a stop string). If it has finished, return its blocks to the pool.

The scheduling stage has two queues: running (the ones being computed) and waiting (the ones waiting in line; first come, first served, FCFS, by default, or by priority). The scheduler first gives the next token to requests in running (a new block if one is needed), then pulls new requests from waiting. Every time it pulls one, it asks the block manager: are there enough blocks in the pool?

Click Next step. On the left is the block pool. On the right are the two queues. Watch step 4: the pool is empty, and the scheduler has to free space.

What if there are not enough blocks? Preemption

Criterion: the goal is to avoid interrupting requests that have already been running for a long time.

  • The scheduler preempts the lowest-priority request (under FCFS, that is the latest arrival): it returns all of that request’s blocks to the pool and puts the request at the front of waiting.
  • A preempted request, once there is room, runs Prefill again and recomputes K and V for “the original prompt + the tokens already generated.” This is called recompute preemption. The official blog says: V1 uses recomputation; V0 also supports swapping the KV out to CPU memory (swap).
  • Why is recomputing workable? (derived from the mechanism, not from a vendor document) Prefill computes a whole sequence in parallel in one pass, much faster than Decode one token at a time, so recomputing a few hundred tokens is often cheaper than moving the whole KV back and forth over PCIe. For the actual tradeoff, follow the official docs and measurements on your own workload.

Split a long prompt into small chunks so requests that are already generating are not stuck behind it

Two words first. Prefill: once the user’s prompt arrives, the whole prompt (possibly thousands of tokens) is computed in one pass and written into the KV Cache. This step is parallel, computes many tokens at once, and is compute-bound.Decode: after that, tokens are generated one by one, and each request computes only 1 token per step.

What do “compute-bound” and “bandwidth-bound” mean? (an order-of-magnitude estimate)

Criterion: in one step, see whether the GPU is waiting on compute or waiting on data.

  • Compute: how many multiply-adds the GPU can do per second. GPU memory bandwidth: how much data GPU memory can deliver to the compute units per second. Think of it as how wide the road is from the warehouse to the factory (GPU memory capacity is how big the warehouse is. The two are different things). compute-bound = the data has already arrived, and the compute units cannot keep up; bandwidth-bound = the compute units are fast, but they keep waiting on data.
  • Take an 8-billion-parameter FP16 model. The weights are about 16GB. GPU memory bandwidth, using the H200’s 4.8TB/s: reading the weights once takes 16GB ÷ 4.8TB/s ≈ 3.3 milliseconds.
  • One Decode step computes only 1 token, about 16 GFLOPs (parameter count × 2). At a scale of about 1000 TFLOPS that takes about 0.016 milliseconds. Reading the data is about 200 times slower than computing it, so Decode is bandwidth-bound.
  • Prefill reads the weights once and can compute thousands of tokens. Compute time far exceeds read time, so it is compute-bound.
  • This is also why the batch size should be large: the 3.3 milliseconds to read the weights once is fixed. About 200 tokens computed together in the same step is what fills the compute. (The compute numbers are approximate values from memory. I did not check each one.)

What is V1? vLLM has two generations of engine. The old one is called V0, the new one is called V1, and it rewrote the core loop and the scheduler (see the official blog “vLLM V1: A Major Upgrade to vLLM's Core Architecture”). The step() loop and the block management in this article are the V1 form.

Now a problem: if one step does only one kind of work, a very long prompt takes over the whole step. Requests that are already generating have to wait for it to finish before they can emit the next token, and the user sees the output stall for a moment.

V1’s method: the scheduler no longer separates a “Prefill step” and a “Decode step.” Instead it gives each step a fixed cap on work, called the token budget, for example at most 8 tokens per step. The order of assignment is: (1) each request that is decoding takes 1 token first (they only need 1 per step anyway); (2) the remaining budget goes to queued prompts, for Prefill.

Example: the budget is 8, 3 requests are decoding, and a new 20-token prompt arrives. Each step gives 3 tokens to Decode and the remaining 5 to the new prompt. 20 ÷ 5 = 4, so it finishes in 4 steps. During these 4 steps those 3 requests still emit 1 token every step, and none of them is interrupted. The long prompt is cut into small chunks and finished over several steps. That is Chunked Prefill. The official docs say it is on by default when it is feasible.

Drag the slider to change the token budget per step. The smaller the budget, the finer the prompt is sliced, and the more steps Prefill takes, but requests that are decoding are left alone at every step.

Budget size is a tradeoff between throughput and latency. A large budget means high GPU utilization and a fast Prefill, but each step takes longer. A small budget means a short step and smoother output, but Prefill is stretched over more steps.

The scheduler and the block manager work together inside the same loop

Put the earlier pieces together. Note that the KV cache manager and the scheduler live in the same loop: every time the scheduler assigns one token, it asks the block manager for a block, and the block manager tells the scheduler how many free slots remain.

vLLM’s main path (simplified). The API server handles HTTP, tokenization, and detokenization. Inside EngineCore are the scheduler and the block manager. What actually runs the model is the worker on the GPU. It uses the PagedAttention kernel, and CUDA graph to cut the overhead of launching kernels.

The shorter the requests, the more paging fits beyond reservation; at the maximum length they tie

Back to the question at the start: how many more requests does this fit? Use the numbers above (a 12GB KV region, 0.8MB per token). The old method reserves the maximum length of 2048 and can hold only ⌊12000/1678⌋=7 of them. After paging, each request occupies only its real length (rounded up to a multiple of 16).

Drag the slider to change the average real length of a request. The shorter the request (relative to the maximum length), the more the old method wastes, and the larger the gain from paging. When the average length is close to 2048, the two are no different.

This is one source of the “2–4× throughput” in the paper: the same GPU memory can hold more requests at once, and the batch the GPU handles each step is larger, so the compute gets fed (derived from the mechanism, not from a vendor document; the paper’s 2–4× was measured on specific models, datasets, and the systems it was compared with).

Paging is not free

Criterion: any indirect addressing has a cost.

  • Each sequence wastes at most the unfilled slots in the last block (a larger block wastes more of this; a smaller block makes a longer block table and more lookups).
  • The PagedAttention kernel has to read non-contiguous GPU memory through the block table. The later vAttention paper argues that this brings programming and performance overhead, and reports that vLLM’s kernel is slower than FlashAttention-2 (their measured result; I did not verify it independently).
  • What paging solves is GPU memory utilization. It does not make a single step of a single request faster.

Six optimizations, each for one bottleneck, stacked on the main path

Each item below is an important feature in vLLM. This article only points out how it relates to the main path, and does not expand it.

  • prefix caching: after a request finishes, blocks are not cleared at once, and are reused by hash. See The Illustrated Prefix Caching.
  • Speculative Decoding: a small model guesses a few tokens first, and the large model checks them in one pass. A step may produce more than 1 token, so when the scheduler computes “how many new tokens this step adds,” it has to account for that.
  • Tensor Parallelism: when the model is too big for one card, each layer’s matrices are split across several GPUs, and the KV Cache is split across the cards with them.
  • Disaggregated Prefill/Decode: Prefill and Decode are split onto different machines. One group of machines only reads prompts (Prefill, compute-bound), and another group only emits tokens (Decode, bound by GPU memory bandwidth). After the prompt is computed on a Prefill machine, the KV blocks it produced are sent over the network to a Decode machine, which continues generating. The two sides do not get in each other’s way. Each is given hardware and tuned for its own bottleneck. The cost is sending the KV, and it is not always worth it when the prompt is very short (derived from the mechanism, not from a vendor document).
  • CUDA Graphs: a whole sequence of GPU operations is recorded in advance and replayed in one shot at runtime, saving the CPU cost of launching a kernel every time (especially useful for short Decode steps).
  • Quantization: store the weights at lower precision (and sometimes the KV too). That saves GPU memory, and lets the same GPU memory hold more requests.

When tuning, start from how many tokens the KV cache can hold

  1. Look first at how much the KV Cache can hold: the startup log reports the GPU KV Cache capacity (counted in tokens). This number, not “how large GPU memory is,” is the ceiling on how many requests can run at once.
  2. --gpu-memory-utilization: the fraction of GPU memory vLLM reserves for itself. After the weights and the intermediate results, the rest goes to the KV block pool. Turning it up means a larger block pool, but leave room for other processes.
  3. --max-model-len: the maximum number of tokens in a single request. Set it larger than you actually need, and the engine treats a single request as possibly expensive, which changes how many requests can be admitted at once. Set it to what the workload actually needs.
  4. --max-num-seqs and --max-num-batched-tokens: the first limits how many requests run at once. The second is the per-step token budget described above. They set the balance between throughput and latency.
  5. Send requests that share a prefix to the same instance: prefix caching works only inside a single engine. Put the prefix at the front of the prompt, and put content that changes (timestamps, usernames) at the end.
  6. Look at the metrics. Do not guess: watch the number of queued requests (waiting), how full the KV block pool is, and the preemption count. Frequent preemption means the block pool is too small or concurrency is too high.
  7. Defaults, and the differences between V0 and V1, change with the version: follow the official docs for the version you use. This article did not check every default.

Mark the parking lot into small spaces and hand them out as cars arrive, and almost nothing is wasted

  1. A GPU is like a big parking lot. Each car is a request that is in the middle of a chat.
  2. The old method: when a car arrives, no matter how big it is, first rope off a large contiguous stretch of spaces, in case it wants to grow. Most of the spaces stay empty, and other cars cannot get in.
  3. vLLM’s method: draw the lot into many small spaces. When a car arrives, give it one or two spaces first. When it needs more, give it one more. The spaces do not have to be next to each other.
  4. Each car holds a small slip that says “my space 1 is at 7, my space 2 is at 1…”. That slip is the block table.
  5. Two cars need to carry the same thing? Their slips point at the same space, and it is stored once. Whoever wants to change it gets a copy first.
  6. When a car leaves, its spaces free up at once for the next car. The lot has almost no waste, and several times as many cars can park.

GPU memory is the bottleneck: paging plus per-step scheduling lets the same GPU serve several times as many requests

  • The problem is GPU memory: on an A100 with a 13B model, the KV Cache is only about 30% of GPU memory, and that sets how many requests can run at once.
  • The old method wastes: contiguous reservation at the maximum length means only 20.4%–38.2% actually stores tokens.
  • PagedAttention: fixed-size blocks plus a block table, allocated on demand, so waste shrinks to the leftover of the last block. The paper measured 96.3% effective.
  • Sharing: a reference count plus copy-on-write, the basis of parallel sampling and prefix caching.
  • Scheduling: each step schedules, then runs the forward pass, then postprocesses; a token budget mixes Prefill and Decode; when blocks run out, recompute preemption.
  • The cost: indirect addressing has overhead, and the kernel has to be written specially. Paging does not speed up a single step of a single request.
