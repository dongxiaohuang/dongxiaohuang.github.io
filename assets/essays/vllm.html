图解 vLLM

把同一个模型、同一块 GPU，换一个推理引擎，吞吐量能差出 2–4 倍（vLLM 论文在同等延迟下的测量）。而且这些 GPU 的算力常常没有跑满，显存（GPU memory，也叫 VRAM）却已经“满”了。这篇文章要回答：显存到底被什么占满了？vLLM 凭什么能用同样的显存多装几倍的请求？

线索只有一个：把 KV Cache 当成操作系统的内存来管理。我们沿用《图解 Transformer》的做法：先从外部看一台推理服务器怎么接请求，再一步步打开它的显存、调度器和 GPU。

这是《图解 KV Cache》和《图解 Prefix Caching》的续篇：前者讲 K、V 为什么可以存下来，后者讲跨请求怎么复用。这一篇讲这些 K、V 在 GPU 显存里到底怎么摆，以及一个引擎怎么每一步决定谁先算。

请求长短不一：短的早早结束，长的一直占着名额

让我们先从外部看。一台推理服务器是一个“请求进、token 出”的接口。请求在不同时间到达，有的 3 步就结束，有的要占 8 步。下图：batch size = 4（同一步最多同时跑 4 个请求），6 个请求（演示值）。三个词标在图上——左边每一行是 batch 里的一个位置，每一列是一个解码步（这一列里每个在 batch 里的请求吐出 1 个 token），色条上的数字是生成步数。

这三个词为什么会出现？ 因为 GPU 服务器有两个事实，逼着你必须这样想：

- 请求（request）：一个用户的一次提问。服务器不是只服务你一个人，同一时刻有很多人在问，每个人的提问就是一个请求。 - 解码步（decode step，也叫 iteration）：大模型一次只能吐 1 个 token，下一个 token 要等上一个出来才能算（自回归）。所以一个 100 字的回答，要把整个模型从头到尾算 100 遍，每算一遍就是一步。步是模型的最小节拍。 - 批大小（batch size）：每一步，GPU 都要把几十 GB 的模型权重读一遍，这个成本是固定的。多带几个请求一起算，几乎不多花时间，所以一起算最划算。但一起算的请求数有上限（显存放不下更多人的 KV Cache），这个上限就是 batch size。batch size = GPU 同一步里同时服务的请求数（vLLM 里对应参数 max_num_seqs；真实系统里它还受 KV Cache 显存限制，不是固定值）。

图里取 4 只是为了画得下；真实服务器可以是几十上百个。一句话：很多请求排队，每步只能让 batch size 那么多的请求各前进一格。

图里的 A–F 就是 6 个不同用户的请求，字母本身没有别的含义：A 只是打个招呼，回答很短（3 步）；B 要写一篇长文，回答很长（8 步）；C 查天气（4 步）、D 写摘要（6 步）、E 翻译一句话（4 步）、F 回一声“好的”（3 步）。同一时刻 batch 里只有 4 个位置，所以后来的人要等。这张图只展示问题：有人早早走了，有人一直占着。位置空出来之后怎么补，旧办法和新办法各是什么，是下一张图的事。

4 个收银台、6 个顾客。买 3 件的先走，空出收银台；买 8 件的一直占着。满了，后来的人在「排队」那一行等。

点 Next step，从左往右看。每个字母是一个用户请求：A 打招呼（3 步）、B 写长文（8 步）、C 查天气（4 步）、D 写摘要（6 步）、E 翻译句子（4 步）、F 回一声好（3 步）。A、B 先到，C、D 把 batch 的 4 行坐满；E 来了没位置，就在排队那一行等；A 只走 3 步，下一列 E 坐下，B 的色条一直铺到第 8 列。F 要等 C 走了才能进 batch。

问题就出在这里：第 3 步 A 走了，第 4 步那一行是空着等，还是马上让排队的 E 补进来？这两种做法，下一张图把它们并排放在一起比。

点 Next step 看关键时刻。上排静态批处理：A 走了那一行空着（粉灰 = 浪费），要等最慢的 B 整批结束，E、F 才能进来。下排连续批处理（continuous batching）：A 一走立刻让 E 顶上。橙框标出本步发生的事。

注意：同样 6 个请求，静态批处理要 12 步、batch 利用率约 58%；连续批处理 8 步、约 88%。灰色越多，GPU 越闲——这是“调度”层面的浪费，还没扯到显存。vLLM 的做法是每一步都重新决定本步算谁（后面“调度器”一节）。

但连续批处理有一个前提：新请求补进来时，显存里要有地方放它的 KV Cache。接下来看显存。

能同时服务多少请求，取决于 KV Cache 那约 30% 的显存

以论文的例子为准：一个 13B 参数的模型在一块 40GB 的 A100 上，约 65%（26GB）的显存放模型权重，接近 30% 放 KV Cache，剩下是中间结果。权重是固定的，能给更多请求用的只有这 30%。所以能同时服务多少个请求，几乎就等于 KV Cache 区域能装下多少个请求。

上排：显存的构成。下排：在 KV Cache 这块区域里，真正存着 token 的 K、V 的比例。论文里对比的旧系统平均只有 20.4%–38.2%，vLLM 达到 96.3%。

一个 token 的 KV 有多大？（按论文的 OPT-13B 算）

判据：每个 token 要为每一层各存一份 K 和一份 V。

  • OPT-13B 有 40 层，隐藏维度 5120，FP16 每个数 2 字节：2×5120×40×2=819,200 字节，约 0.8 MB / token（论文写 800 KB）。
  • 一个最长 2048 token 的请求，KV 最多 2048×0.8 MB≈1.6 GB（论文同样给出 1.6GB）。
  • 12GB 的 KV 区域，如果每个请求都按 2048 token 预留，只能放 7 个请求。这就是下一节的问题。

论文里的 40GB 是 2023 年的 A100，今天的卡显存大得多。下表是几款常见 GPU 的单卡显存（2026-11-24 查询，数字以厂商官方页面为准，非官方来源已标出）：

数据中心卡大致从 80GB 走到了 190–290GB。显存越大，扣掉模型权重后留给 KV Cache 的区域就越大，同时能服务的请求也越多。但模型也在变大，所以“KV Cache 占多少”这个问题并没有消失，只是数字搬到了更大的量级。

接口上的 max_tokens（也叫 max_completion_tokens）只限制这一次最多再生成多少个 token，不算 prompt。上面的 2048 是整段上限：prompt 加上还要生成的。prompt 已经占掉的加上 max_tokens，不能超过模型的 context；静态预留仍按这个整段上限占 KV。vLLM 的 SamplingParams.max_tokens 也只是「最多再生成多少个」。

按最大长度预留，让 KV 显存里只有 20%–38% 真正存了 token

上一节讲的是：batch 里的位置空出来，要马上补人。但这个 batch 一共能有几个位置（batch size），由显存最多能装下几个请求的 KV Cache 决定。旧做法恰恰在这里浪费了大半，把 batch size 压得很低。两层各管一件事，要一起解决才有效：

管什么旧做法的问题新做法
调度batch 里的位置空了怎么办空着等最慢的请求每一步都补人（连续批处理）
显存batch 最多能有几个位置按最大长度预留，浪费显存，batch size 被压低分页按需分配，batch size 能做大

只有连续批处理、没有分页：batch 想补人，却可能因为显存被预留占满而补不进去。只有分页、没有连续批处理：位置空了还是得等整批结束才补。

请求进来时，系统不知道它最终会生成多长。最稳妥的做法是：先按最大长度（比如 2048）在显存里划一整块连续的空间。这样做有三种浪费（论文的分类）：

浪费是什么为什么发生
预留（reservation）给未来 token 留着、但眼下还没用到的槽位这个请求还在生成，别的请求用不上这块地
内部碎片（internal fragmentation）预留了 2048，实际只生成 200，剩下 1848 永远用不上事先不知道输出多长
外部碎片（external fragmentation）空闲空间一共够，但被切成零碎小块，凑不出一整块连续的每个请求都要一块连续区域

这三种加起来，旧系统里只有 20.4%–38.2% 的 KV 显存真正存着 token（上一张图）。根源在于“连续”这个要求：因为每个请求都要一整块连续地址，所以必须预留，所以必须浪费。

PagedAttention 把 KV Cache 切成小块按需分配，浪费降到只剩最后一块的零头

先想一个问题：一个请求的 KV Cache 是一个 token 一个 token 长出来的，没人知道它最后会有多长。旧做法是一次要一整块大的，上一节已经看到有多浪费。能不能用多少给多少？

打个比方：你要记笔记，但不知道会记多少页。

  • 旧做法：先买一本 2048 页的大本子，万一写满呢？结果只写了 6 页，剩下的白白占着，别人也不能用。而且这本子必须整本放在书架上，书架没有这么大的空位就放不进去。
  • 新做法：用小便签，每张只有 4 行。写满一张，再拿一张。便签可以随手塞进抽屉里任何一个空位，不用挨着放。你只要有一张目录：“第 1 张在 7 号抽屉，第 2 张在 1 号抽屉……”。

把这个比方对应到 KV Cache，就是下面四个词（也是图里出现的词）：

  • 块（block） = 一张便签：大小固定，存固定个数的 token 的 K、V。vLLM 默认一块存 16 个，图里为了画得下，一块只放 4 个。
  • 逻辑块（logical block） = 你眼里的“第 1 张、第 2 张”：请求自己按顺序编号 0、1、2……，在它看来这些块是连续的。
  • 物理块（physical block） = 抽屉里真实的位置：GPU 显存里的真实块，可以散在任何地方。
  • 块表（block table） = 目录：记录“第几个逻辑块 → 第几号物理块”。

这和操作系统管内存的“分页”是同一个想法（块 ≈ 页，块表 ≈ 页表），所以叫 PagedAttention。

读图：上面两行是请求 A（蓝）、请求 B（橙）眼里看到的逻辑块，下面一行是显存里真实的 8 个物理块，中间的连线就是块表。点 Next step，一共 5 步：

  1. A 到达：提示词有 6 个 token，只拿 2 张便签（逻辑块 0、1），目录记下它们在 7 号和 1 号物理块。
  2. B 到达：拿 2 张，放在 4 号和 6 号。A 和 B 的块在显存里交错摆放，但各自看起来都是连续的。
  3. A 又生成 2 个 token：写进最后一张便签的空位，不用拿新的。
  4. A 的最后一块写满了：这时才再拿一块（逻辑块 2 → 3 号物理块），目录里多一条线。
  5. A 结束：它的 3 块立刻还回空闲池（虚线框），下一个请求马上能用。B 不受影响。

点 Next step 一步步看。上面两行是两个请求“以为自己看到的”连续的逻辑块，下面一行是 GPU 里真实的 8 块物理显存，中间的连线就是块表（蓝 = A，橙 = B）。橙色描边的格子是这一步新写入的 token：A 和 B 的块在显存里交错摆放，但各自看起来是连续的。

这样，上一节的三种浪费就都解决了：没有预留（用多少拿多少）；内部碎片只剩最后一块里没写满的那几格（最多 15 个 token，而不是上千个）；外部碎片没有了（所有块一样大，任何空闲块都能给任何请求用，不会出现“总空间够，却凑不出一整块”）。

为什么 attention 能在“散落”的块上算？（原理推导）

判据：每个历史 token 的分数 q·kj 只用到它自己的 K，和别的 token 放在哪、挨不挨着无关。

  • 先回顾 attention 做什么：新 token 的 Query（q）和每个历史 token 的 Key（kj）点乘，得到分数 sj=q·kj；softmax 把分数变成权重 αj=esj∑lesl；最后对 Value 加权求和 o=∑jαjvj。
  • 第一步 q·kj 不怕散：每个 j 各算各的，K 放在哪个块都行。内核查块表找到那一块，取出 K，就能算。
  • 需要“整体”的只有 softmax（要所有分数的总和）。办法是每个块先算自己的两样东西：∑es 和 ∑esv，最后把各块的加起来再相除，结果和一次算完完全一样。（实际实现还会减去最大分数来防止溢出，这就是 FlashAttention 一类算法用的“在线 softmax”。）
  • 小例子：3 个历史 token，分数 2、1、3，对应的 v 是 1、2、3。块 X 存前两个：∑es=7.39+2.72=10.11，∑esv=7.39×1+2.72×2=12.83。块 Y 存第三个：∑es=20.09，∑esv=20.09×3=60.26。合并：(12.83+60.26)÷(10.11+20.09)≈2.42，和不分块直接算一样。
  • 所以 PagedAttention 的 GPU 内核不要求 K、V 连续：它查块表，一块一块取出来算。代价是多了一次查表、内存访问不连续，内核要专门写（论文称之为 PagedAttention kernel）。

相同的内容只存一份，要改的时候才复制

分页还带来一个意外的好处：多个请求可以指向同一个物理块。典型场景是并行采样（parallel sampling，同一个提示词生成多个候选回答）、束搜索（beam search），以及上一篇讲的前缀缓存。它们的提示词 K、V 完全一样，没必要存多份。

共享的难点在于：谁往共享的块里写，会影响别人。vLLM 的做法和操作系统一样：给每个物理块记一个引用计数，写之前检查——计数大于 1 就先写时复制（copy-on-write）。

点 Next step。S1 先写：块 P1 被共享（ref=2），所以先复制成 P2 再写；S2 再写时 P1 只剩它一个人用（ref=1），原地写即可。

前缀缓存是同一个机制的延伸：请求结束后，物理块先不清空，按“内容哈希”留在池子里；下一个请求的开头如果哈希相同，块表直接指向这些块，不用重算。细节见《图解 Prefix Caching》。

调度器每一步都重新决定谁算，块不够就让出空间

有了块，就可以说清楚引擎是怎么转的。vLLM（V1）里引擎核心（EngineCore）只干一件事：反复调用 step()。每一步有三个阶段：

  1. Schedule（调度）：决定本步算哪些请求、各算几个 token。
  2. Forward（前向）：GPU 跑一遍模型，采样出下一个 token。
  3. Postprocess（后处理）：把新 token 追加到请求上，检查是否结束（EOS、长度上限、停止词）；结束了就把它的块还给池子。

调度阶段有两个队列：running（正在算的）和 waiting（排队的，默认先来先服务 FCFS，也可以按优先级）。调度器先给 running 里的请求续上下一个 token（必要时要新块），再从 waiting 里拉新请求，每拉一个都要问块管理器：池子里够不够块？

点 Next step。左边是块池，右边是两个队列。注意第 4 步：池子空了，调度器必须让出空间。

块不够了怎么办？抢占（preemption）

判据：目标是让已经跑了很久的请求尽量不被打断。

  • 调度器会抢占优先级最低的请求（FCFS 下就是最后到的）：把它的块全部还给池子，把它放回 waiting 的前面。
  • 被抢占的请求，等有空间时重新做一次 Prefill，把“原提示词 + 已生成的 token”重新算出 K、V。这叫重算式抢占（recompute preemption）。官方博客说明：V1 用的是重算；V0 还支持把 KV 换到 CPU 内存（swap）。
  • 为什么重算可行？（原理推导）Prefill 是一次性并行算完一整段，比逐个 token 解码快得多，所以重算几百个 token 往往比通过 PCIe 来回搬运整块 KV 更划算。具体取舍请以官方文档和你的负载实测为准。

把长提示词切成小块，正在生成的请求就不会被它卡住

先说两个词。Prefill（预填充）：用户的提示词一进来，要把整段提示词（可能几千个 token）一次性算完，写进 KV Cache。这一步是并行的，一次算很多 token，很吃算力。Decode（解码）：之后一个 token 一个 token 往外生成，每个请求每一步只算 1 个 token。

什么叫“吃算力”和“吃带宽”？（量级估算）

判据：看一步里，GPU 是在等计算，还是在等数据。

  • 算力：GPU 每秒能做多少次乘加运算。显存带宽：显存每秒能把多少数据送到计算单元，可以想成仓库到工厂那条路有多宽（显存容量则是仓库有多大，两者不是一回事）。吃算力 = 数据早就送到，计算单元忙不过来；吃带宽 = 计算单元很快，却总在等数据。
  • 拿一个 80 亿参数、FP16 的模型举例，权重约 16GB。显存带宽取 H200 的 4.8TB/s：把权重读一遍要 16GB ÷ 4.8TB/s ≈ 3.3 毫秒。
  • Decode 一步只算 1 个 token，约 16 GFLOPs（参数量 × 2），按约 1000 TFLOPS 的量级只要约 0.016 毫秒。读数据比算数据慢约 200 倍，所以 Decode 吃带宽。
  • Prefill 读一遍权重就能算几千个 token，计算时间远超读取时间，所以 吃算力。
  • 这也解释了为什么要把 batch size 做大：读一遍权重的 3.3 毫秒是固定的，同一步里约 200 个 token 一起算，才能把算力用满。（算力数字是我凭记忆取的约值，没有逐项核实。）

V1 是什么？ vLLM 有两代引擎：老的叫 V0，新的叫 V1，把核心循环和调度器重写了一遍（见官方博客《vLLM V1: A Major Upgrade to vLLM's Core Architecture》）。本文讲的 step() 循环、块管理，都是 V1 里的样子。

现在有个问题：如果一步只做一种事，那么一个很长的提示词来了，这一步就全被它占了。正在生成的请求要等它算完才能吐出下一个 token，用户会看到输出突然卡一下。

V1 的做法：调度器不再把“Prefill 步”和“Decode 步”分开，而是给每一步一个固定的工作量上限，叫 token 预算（token budget），比如每步最多算 8 个 token。分配顺序是：（1）每个正在解码的请求先拿 1 个 token（它们每步本来就只要 1 个）；（2）剩下的预算，分给排队的提示词做 Prefill。

例子：预算 8，有 3 个请求正在解码，来了一个 20 个 token 的新提示词。每一步 3 个 token 给解码，剩下 5 个给新提示词，20 ÷ 5 = 4 步就算完了。这 4 步里，那 3 个请求每步都照常吐出 1 个 token，一次都没被打断。长提示词被切成小块、分几步算完，这就是 Chunked Prefill（分块预填充）。官方文档说明在可行时默认开启。

拖动滑块改变每步的 token 预算。预算越小，提示词被切得越碎，要更多步才能 Prefill 完，但解码中的请求每一步都不受打扰。

预算大小是吞吐和延迟的取舍：预算大，GPU 利用率高、Prefill 快，但每步耗时变长；预算小，每步短、输出更平滑，但 Prefill 要拖更多步。

调度器和块管理器在同一个循环里互相配合

把前面的部分拼在一起。注意 KV 缓存管理器和调度器住在同一个循环里：调度器每分配一个 token，都要向块管理器要块；块管理器告诉调度器还有多少空位。

vLLM 的主干（简化）。API 服务器负责 HTTP、分词和反分词；EngineCore 里是调度器和块管理器；真正跑模型的是 GPU 上的 worker，它使用 PagedAttention 内核，并用 CUDA graph 减少内核启动开销。

图里省略了很多东西：多 GPU 的张量并行、多个 API 进程、Prefill/Decode 分离部署、推测解码等等，后面的“进一步优化”会点到。

请求越短，分页比预留多装的请求越多；接近最大长度时两者没差别

回到最开头的问题：这能多装多少请求？用上面的数字（12GB 的 KV 区域、每个 token 0.8MB）算一下。旧做法按最大长度 2048 预留，只能装 ⌊12000/1678⌋=7 个；分页后每个请求只占自己真实长度（向上取整到 16 的倍数）。

拖动滑块改变请求的平均真实长度。请求越短（相对最大长度），旧做法浪费得越多，分页的收益越大；平均长度接近 2048 时，两者就没有差别了。

这就是论文里“2–4 倍吞吐”的来源之一：同样的显存能同时装下更多请求，而每一步 GPU 处理的批更大，算力就被喂饱了（原理推导；论文的 2–4 倍是在特定模型、数据集和对比系统下测得的）。

分页不是免费的

判据：任何间接寻址都有成本。

  • 每个序列最多浪费最后一个块里没填满的槽位（块越大，这个浪费越大；块越小，块表越长、查表越多）。
  • PagedAttention 内核要通过块表读取不连续的显存。后来的 vAttention 论文认为这带来了编程和性能开销，并报告 vLLM 的内核比 FlashAttention-2 慢（他们的测试结果，我没有独立核实）。
  • 分页解决的是显存利用率；它不会让单个请求的单步计算更快。

这六项优化各管一个瓶颈，叠加在主干之上

下面每一项都是 vLLM 里的重要功能，本文只点出它和主干的关系，不展开。

  • Prefix Caching（前缀缓存）：请求结束后块不立刻清空，按哈希复用。见《图解 Prefix Caching》。
  • Speculative Decoding（推测解码）：用小模型先猜几个 token，大模型一次验证。每步可能产出不止 1 个 token，所以调度器计算“本步新增 token 数”时要考虑它。
  • Tensor Parallelism（张量并行）：模型太大一块卡放不下时，把每层的矩阵切到多块 GPU 上，KV Cache 也跟着分到各卡。
  • Disaggregated Prefill/Decode（Prefill 与 Decode 分离）：把 Prefill 和 Decode 拆到不同的机器上做：一批机器专门读提示词（Prefill，吃算力），另一批专门吐 token（Decode，吃显存带宽）。提示词在 Prefill 机器上算完后，把生成的 KV 块通过网络传给 Decode 机器，由它接着往下生成。这样两边互不干扰，各自按瓶颈配硬件、调参数；代价是要传 KV，提示词很短时不一定划算（原理推导）。
  • CUDA Graphs：把一整串 GPU 操作预先录下来，运行时一次性重放，省掉每次启动内核的 CPU 开销（对短小的解码步特别有用）。
  • Quantization（量化）：用更低的精度存权重（有时也存 KV），既省显存，也让同样的显存装更多请求。

调优先看 KV 能装多少 token，而不是显存有多大

  1. 先看 KV 能装多少：启动日志里会报告 GPU KV Cache 的容量（以 token 计）。这个数字，而不是“显存多大”，才是并发能力的上限。
  2. --gpu-memory-utilization：vLLM 预留给自己的显存比例，扣掉权重和中间结果后，剩下的都划给 KV 块池。调高 = 块池更大，但要给其他进程留余地。
  3. --max-model-len：单个请求最长多少 token。设得比实际需要大，会让引擎认为单请求可能很贵，影响能同时接纳的请求数。按业务实际需要设。
  4. --max-num-seqs 与 --max-num-batched-tokens：前者限制同时运行的请求数，后者就是上面讲的每步 token 预算。它们影响吞吐与延迟的平衡。
  5. 同一个前缀的请求尽量走同一个实例：前缀缓存只在单个引擎内生效；前缀放在提示词最前面，易变的内容（时间戳、用户名）放在最后。
  6. 看监控，不要猜：关注排队的请求数（waiting）、KV 块池的使用率、以及抢占次数。抢占频繁说明块池太小或并发太高。
  7. 各参数的默认值和 V0/V1 的差别会随版本变：以你所用版本的官方文档为准，本文没有核实每个默认值。

停车场画成小格子，车来了才给格子，就几乎没有浪费

  1. GPU 像一个大停车场，每辆车就是一个正在聊天的请求。
  2. 以前的做法：每辆车来的时候，不管它多大，都先给它圈一大片连续的车位，万一它想长大呢？结果车位大半都空着，别的车进不来。
  3. vLLM 的做法：把停车场画成很多小格子。车来了，先给一两个格子；它需要更多，再给一格。格子不用挨在一起。
  4. 每辆车拿着一张小纸条，上面写着“我的第 1 格在 7 号、第 2 格在 1 号……”。这就是块表。
  5. 有两辆车要装同样的东西？它们的纸条指向同一个格子，只存一份；谁要改，就先复印一份给他。
  6. 车开走了，格子马上空出来给下一辆。停车场几乎没有浪费，能停下的车多了好几倍。

显存才是瓶颈：分页加上每步调度，让同一块 GPU 多服务几倍请求

  • 问题在显存：13B 模型的 A100 上，KV Cache 只占约 30% 的显存，决定了并发请求数。
  • 旧做法浪费：按最大长度连续预留，只有 20.4%–38.2% 真正存了 token。
  • PagedAttention：固定大小的块 + 块表，按需分配，浪费降到最后一块的零头，论文测得 96.3% 有效。
  • 共享：引用计数 + 写时复制，并行采样和前缀缓存的基础。
  • 调度：每个 step 先调度、再前向、后处理；用 token 预算混合 Prefill 和 Decode；块不够时重算式抢占。
  • 代价：间接寻址有开销，内核要专门写；分页不加速单个请求的单步计算。
