图解 Prefix Caching（前缀缓存）

打开 Agent 的请求日志，你会发现一件奇怪的事：每一轮请求的开头几乎一模一样——同一份系统提示词、同一份工具定义、一路累积下来的对话历史。模型每次都老老实实把它们从头读一遍（Prefill），账单也每次都按“新输入”收钱。

而价格页上，命中缓存的输入比没命中的便宜 10–50 倍。这篇文章要回答：模型凭什么敢说“这段我读过了”？它怎么在毫秒内找到上次读过的那一段？又有哪些写法会把缓存弄坏？

这是《图解 KV Cache》的续篇。那一篇讲了 K、V 为什么可以存下来；这一篇讲跨请求把它们接着用。读过 KV Cache 那篇会更顺，没读过也没关系，需要的部分会再说一遍。

先看现象：Agent 每一轮都在重复劳动

让我们先从外部看。一个 Agent 会话里，用户问一句、模型答一句，下一轮请求要把整段对话重新发一遍。下图是三轮请求，每个方块是一段内容，方块下的数字是 token 数（演示值）。

三轮请求。点上方的开关切换“没有 / 有前缀缓存”，看右边“计算了多少 token”。绿色 = 命中缓存，粉色 = 需要 Prefill。

注意：没有缓存时，三轮共要 Prefill 3,200 + 3,700 + 4,200 = 11,100 个 token；有缓存时只要 3,200 + 500 + 500 = 4,200 个。新增的内容其实只有 500 来个，剩下的都是在重算已经算过的东西。随着对话变长，这个差距还会越拉越大。

前缀缓存（Prefix Caching） 要做的事很朴素：把上一次 Prefill 算出的 K、V 留下来，下一个请求如果开头相同，就直接用，只算新增的部分。

为什么必须是“前缀”

为什么缓存只认开头一致，不能“中间有一段相同也行”？这是因为 K、V 不只取决于词本身，还取决于它左边的所有词。

为什么 K、V 只能按前缀复用？（原理推导）

判据：一个词在某一层的 K、V，是由“这个词和它左边的所有词”决定的。

  • 解码器的自注意力带遮罩：第 $i$ 个词只能看到第 1 到第 $i$ 个词，看不到右边。
  • 第 1 层里，第 $i$ 个词的输出只依赖 $t_1,\dots,t_i$；第 2 层的输入就是第 1 层的输出，所以第 2 层里它仍然只依赖 $t_1,\dots,t_i$。一层层推下去，每一层都一样。
  • 因此第 $i$ 个词的 K、V 可以写成 $K_i, V_i = f(t_1,\dots,t_i)$：只要这 $i$ 个词（连同它们的位置）不变，K、V 就一字不差，可以直接拿来用。
  • 反过来：只要第 $j$ 个词变了，从 $j$ 往右的每一个词，它们依赖的“左边”都变了，K、V 全部作废。

点任意一个词把它改掉：它和它右边的 K、V 全部要重算（粉色），左边的仍然可以复用（绿色）。

这条规则决定了后面所有的事：缓存的匹配方式、提示词怎么写、为什么一个时间戳就能毁掉命中率。

怎么在毫秒内找到上次的前缀：分块 + 哈希链（vLLM 的办法）

最笨的办法是把新请求的 token 一个个和历史请求对比，太慢。这一节讲的是开源引擎 vLLM 的做法。分块来自它的 PagedAttention（Kwon et al., SOSP 2023），按哈希自动匹配前缀是 vLLM 在此之上做的 Automatic Prefix Caching。它把提示词切成固定大小的块（block；vLLM 里典型值是每块 16 个 token，下图为了画得下，一块只放 3 个），再给每一块算一个哈希。

关键在于：每一块的哈希，把前一块的哈希也算进去（vLLM 文档的原话是：用块里的 token 和这一块之前的 token 来哈希）。这样第 $i$ 块的哈希就代表了“从开头到这一块”的整段前缀，而不只是这一块自己的内容。除了 token，哈希里还会带上 LoRA ID、多模态输入的哈希、cache salt 这类“让这一块独一无二”的额外信息，免得不同的东西撞在一起。

$$h_i = H\big(h_{i-1},\ \text{tokens of block } i\big),\qquad h_0 = \varnothing$$

请求 A 已缓存。点请求 B 里的词把它改掉：这一块的哈希变了，后面所有块的哈希跟着变，即使后面的内容一字未改，也是 MISS。尾部不满一块的词不进缓存。

vLLM 用一张“哈希 → 块”的哈希表加一条空闲块队列来管理，每个块有引用计数；只缓存装满的块。查缓存就是拿哈希去查表：B 的 $h_1$ 在不在表里？在，命中；$h_2$ 在不在？……直到第一个查不到的，后面就不用查了。这个过程是 $O(\text{块数})$ 的几次哈希表查询，所以是毫秒级。

为什么要分块，而不是按 token 缓存？

判据：管理成本和复用粒度之间的取舍。

  • vLLM 选的是“块 + 哈希表”：元数据（哈希、引用计数）摊薄到每一块一份，查表是哈希表查询。SGLang 选的是另一条路：token 粒度（每页只放 1 个 token）加一棵前缀树，匹配更精细，但要维护一棵树。
  • 显存本来就按块分页管理（vLLM 的 PagedAttention），缓存块和显存块天然对齐，复用时不用拷贝，只是多一个指针指向同一块。
  • 代价：尾部不满一块的 token 没有哈希，不会被缓存；而且命中长度永远是块大小的整数倍。

把很多请求放进一棵前缀树（SGLang 的办法）

一个服务会同时收到成千上万个请求。它们之间有大量共同前缀：同一个产品的所有用户共用同一份系统提示词。如果每个请求各存一份，显存很快就爆了。

SGLang 的办法叫 RadixAttention（SGLang 论文第 3 节，Zheng et al., 2023）：用一棵前缀树（radix tree，基数树）管理“token 序列 → 对应的 KV”，边上标的是一段 token 序列。共同的前缀只存一份“主干”，每个请求各自不同的部分是分出去的“枝条”。vLLM 没有用树，但效果相同：共同前缀的哈希一样，指向的就是同一批块，也只存一份。

用一个小例子看这棵树。 三个请求，每个词当一个 token：

A: You are helpful . Fix this bug
B: You are helpful . Summarize the doc
C: You are helpful . Fix this typo

它们的开头 You are helpful . 一样。树把没有分叉的一串 token 合成一条边，每条边上存着这段 token 对应的 KV：

root ──[You are helpful .]──○──[Fix this]──○──[bug]
                            │              └──[typo]
                            └──[Summarize the doc]

点 Replay 或 Next step：先看三个请求，再看每个 token 一个节点的普通前缀树，再看压缩后的基数树，最后看新请求怎么把一条边劈成两半。

公共的 You are helpful . 只有一份 KV，A、B、C 共用，这就是“主干只存一份”；各自不同的 bug、typo、Summarize the doc 是分出去的枝条。

查缓存就是从根出发，沿着边逐段比对，能比多长就命中多长。来了 You are helpful . Fix this bug，三段边全对上，整条命中。来了 You are helpful . Fix that，第一段对上；第二条边 Fix this 只有 Fix 对上，树就把这条边劈成两半：Fix 归公共部分，this 和 that 各成一根枝条。这就是 radix tree（基数树）和普通 trie（每个节点只放一个 token 的前缀树）的区别：没有分叉的一长串合并成一条边，有分叉时才劈开。

vLLM 不用树：每一块有一个哈希，查的是哈希表。A、B、C 前几块的内容相同，哈希就相同，查到的是同一个块，所以也只存一份。区别只是：SGLang 靠树的结构找到共用的部分，vLLM 靠哈希相同找到共用的部分。

所以前缀树和块哈希作用相同，都是为了找到已缓存的最长公共前缀，并让公共前缀只存一份；只是方法不同：

前缀树（SGLang）块哈希（vLLM）
怎么识别“是同一段前缀”沿着树从根往下，逐段比对 token算出每块的哈希，去哈希表里查
结构一棵树，边上存 token 序列和对应的 KV一张“哈希 → 块”的表，不是树
粒度每个 token每一块（比如 16 个 token）
公共前缀只存一份靠什么它们走的是树上的同一条边它们算出的是同一个哈希，查到同一个块
淘汰先淘汰最久没用的叶子淘汰空闲队列里最久没用的块

块哈希也能起到前缀树的作用，是因为每块的哈希里带着前一块的哈希：“哈希相同”就等于“从开头到这一块都相同”，这本身就是前缀关系。哈希链隐含了一棵树，只是没有把它存成树的结构。

真正的区别在两处：匹配精度（树按 token 匹配，命中长度可以是任意 token 数；vLLM 只缓存装满的块，命中长度是块大小的整数倍，尾部不满一块的要重算）和实现成本（哈希表查找简单；树更精细，但边被劈开时要修改结构）。对使用者来说，效果一样：开头一致就命中，开头不一致就未命中，所以“静态在前、动态在后”对两边都成立。

100 个用户共用一份 1 万 token 的系统提示，只存一份主干（绿色），每个人的问题是一根小枝条（橙色）。点“+ New request”加用户，点一个枝条表示它刚被用过，点“Evict LRU leaf”淘汰最久没人用的枝条。

显存满了怎么办？ 两家都按 LRU（Least Recently Used，最近最少使用） 淘汰，但细节不同：

  • SGLang： 先淘汰最久没用的叶子，叶子删掉后它的父节点变成新的叶子，再按顺序淘汰，所以公共主干最后才会被动。每个节点有引用计数，有正在运行的请求用着（计数不为 0）就不能淘汰；缓存和运行中的请求共用同一块显存池。
  • vLLM： 没人用的块（引用计数归零）进空闲队列，队首是最久没用的，显存紧张时从队首淘汰。一个请求结束时，它的块是按倒序放回队尾的：越靠后的块依赖的前缀越长、越不容易被别人复用，所以先淘汰。

无论哪种，热门主干因为不断被新请求用到，都最不容易被淘汰。

至于 OpenAI、Anthropic、DeepSeek 内部怎么实现，官方文档没公开，只说明了外部行为（前缀匹配、整段一致）。上面是开源引擎的做法，闭源服务大概率思路类似（推测），但别把它们当成这些服务的实现。

把前面几块拼起来，引擎处理一个带缓存的请求，大致是这六步。下图按 vLLM 的块哈希方式画；SGLang 是在树上找最长前缀，其余步骤一样。

以一个 10,050 token 的提示为例（块大小 16）：625 块命中，只需要 Prefill 剩下的 50 个 token。

注意第 4 步：未命中的“尾巴”仍然要做 Prefill，但它的注意力计算会读取已缓存的 10,000 个词的 K、V，就像这些 K、V 是刚刚算出来的一样。命中的部分省掉的是重新计算 K、V（以及它们前面所有层的前向计算），而不是整个注意力的读取。

还有一点：第 6 步把新块登记进缓存，包括这一次生成出来的部分。所以多轮对话里，第 2 轮不仅能命中第 1 轮的提示，通常还能命中第 1 轮的回答（它在第 2 轮里已经变成了输入）。

命中规则只有一条：从第一个 token 开始逐字一致

由于哈希链的缘故，缓存命中是“从头开始的最长公共前缀”。开头只要变一个字，哈希链从根部就断了，后面哪怕有一万字完全相同，也全部未命中。

每个方块是一块内容。点下排的方块表示“这一块变了”。切换 “Timestamp first / last” 看看，同样多的内容，时间戳放在开头还是结尾，命中率差多少。

这就是“前缀污染”：在提示词最前面写了会变的东西，比如当前时间、用户 ID、会话状态、随机数。下面是几个常见的坑：

写法结果改法
系统提示词开头写 Current time: 2026-11-24 14:03:21每次请求开头都不同，整条缓存失效时间放到最后一条用户消息里
对话中途增删工具定义工具列表在前缀里，改一个工具，后面全断工具列表固定，用“是否启用”的字段控制
JSON 序列化时键的顺序不稳定同样的内容，字节不同，哈希不同固定键顺序（排序序列化）
把历史消息“压缩改写”中间一块变了，之后全部未命中只在末尾追加；必须压缩时，接受一次失效
静态文档放在用户问题之后每个问题都把文档挤到不同位置文档在前、问题在后

动态选工具（每轮只给模型一部分工具）一定更快吗？不一定。 它是拿“少算一点”换“缓存失效”：

固定完整工具表动态选工具
工具部分的 token多（比如 5,000）少（比如 1,000）
缓存工具和系统提示都能命中工具表一变，前缀从开头起全部未命中
每轮要 Prefill 的 token只算新增部分，很少整个前缀都要重算（比如约 4,000 个 token）

举个例子：系统提示加工具共 8,000 token，其中工具 5,000。固定工具表时，命中后每轮只算新增的几百个 token；动态选工具时，工具虽然只剩 1,000，但每轮要重新 Prefill 整个 4,000 左右的前缀，反而更慢，输入费用也更高。只有工具表特别大（成百上千个）、而且缓存本来也命中不了（比如请求间隔太长缓存过期）时，少发工具才可能赢。（原理推导，数字是演示值）

不想让模型用某些工具时，别删，要“遮住”。 Manus上下文工程经验（原文：Manus 的博客）的做法是：提示词里的工具表一个字都不改，前缀不变，缓存照常命中；在模型生成输出的那一步限制它：模型每一步会给每个可能的下一个 token 打分（logits），把不该选的工具对应的分压到极低，概率接近 0，模型就选不到它。类比：菜单照常印着所有菜，但点菜时把不能点的几道捂住。注意：库里那页笔记里的 logit_bias 是示意代码，博客原文并没有提 logit_bias，只说“直接屏蔽 token 的 logits”，具体怎么做见下面；托管 API 能不能这样做取决于接口。Anthropic 文档写明改 tool_choice 只会让 messages 部分的缓存失效，tools 和 system 仍然命中，所以“用 tool_choice 限制选择”比“改工具表”便宜得多（其他厂商我没核实）。

Manus 具体怎么做（出自博客“Mask, Don't Remove”一节）： 它先说明为什么不删：工具定义在上下文最前面，改一次，后面所有内容的缓存都失效；而且历史里的动作还引用着被删掉的工具，模型会困惑，容易出现格式错误或编造动作。做法有三件事：

  1. 状态机： 根据当前状态决定这一步允许用哪些工具。博客的例子：用户刚发来新消息时，必须马上回复，不能先去调工具。
  2. 响应预填（response prefill）： 在模型开口之前，先替它写好回复的开头，模型只能接着往下写。Hermes 格式的三档：Auto 只预填 <|im_start|>assistant，模型自己决定调不调工具；Required 预填到 <tool_call>，必须调工具，调哪个不限；Specified 预填到 <tool_call>{"name": "browser_，必须调工具，而且只能是名字以 browser_ 开头的那几个。
  3. 工具名统一前缀： 浏览器类都以 browser_ 开头，命令行类都以 shell_ 开头。预填一个前缀，就能把选择限制在一组工具里。

串起来看：工具表里固定放着 browser_open、browser_click、shell_ls、shell_run 四个，永远不变。当前状态是“正在浏览网页”，就预填 {"name": "browser_，模型只能补成 browser_open 或 browser_click；shell_ 的两个仍然在表里，但这一步选不到。工具表和系统提示都没变，缓存照常命中。博客没有给出状态机或屏蔽的具体代码，预填在各家 API 里是否可用，我没核实。

省多少：延迟和成本

命中的部分不再做 Prefill，所以它同时省两样东西：首字延迟（用户等第一个字的时间）和输入价格。

选一个提示长度，拖动命中率。时间按“每秒 Prefill 5,000 个 token”估算，成本按命中价 = 未命中价的 1/10 估算，都是演示值。

一个算例：32,000 token 的提示，命中 90%。要计算的 token 从 32,000 降到 3,200，首字延迟从 6.4 秒降到 0.64 秒；输入成本是 $0.1 + 0.9 \times 0.1 = 0.19$ 倍，约等于打了两折。命中率 100% 时延迟和成本都不会降到 0，因为命中的块仍然要付读取费用，而且最后几个 token 总是要算的。

需要说明的是：Prefill 的计算量并不严格和 token 数成正比（注意力部分和长度的平方有关），所以真实长上下文里，省下的时间比例通常比图里更大。图里只用了最简单的线性假设。（原理推导）

首字延迟（TTFT，Time To First Token）由什么决定？ 大致是：TTFT ≈ 排队等待 + 未命中部分的 Prefill 时间 + 第一步解码 + 网络和分词

  • 未命中的 token 数： 通常是最大的一项，Prefill 的时间基本随它增长。这正是前缀缓存能降首字延迟的原因：命中的部分不用算。
  • 排队等待： 服务繁忙时请求要先等调度，提示词再短也会慢。
  • 模型大小和硬件： 模型越大、GPU 越少，Prefill 越慢。
  • 缓存从哪里读： 显存里最快；落到 SSD 的（如 DeepSeek）读起来稍慢。
  • 网络和分词： 一般很小。

这是按原理推导的结构，不是哪家官方给的公式；上面滑块图只用了最简单的一项（未命中的 token 数 ÷ 速度）。（原理推导）

代价与边界

  • 占显存或硬盘。 缓存的 KV 不是免费的：它占着显存，显存紧张时会被 LRU 淘汰，所以“昨天的缓存今天还在”并不保证。有的厂商（如 DeepSeek）把 KV 转存到分布式 SSD，换来更大的容量，读起来比显存稍慢。
  • 有存活时间。 缓存只会保留一阵子。Claude 的缓存有 5 分钟和 1 小时两档，OpenAI 价格页上标注了 30 分钟、12 小时两档（以上均为 2026-11-24 价格页，随时间会变，请以官方页面为准）。每次命中会刷新计时。
  • 块粒度带来损耗。 命中长度是块大小的整数倍，尾部不满一块的内容不进缓存；另外有的厂商规定提示太短（比如不到 1,024 token）不缓存，具体门槛以文档为准。
  • 缓存之间是隔离的。 如果不同客户能命中彼此的缓存，就可以通过“响应快不快”反推别人的提示词内容。所以各家通常按账号 / 组织隔离缓存，不会跨客户共享（具体隔离范围请看各家文档）。（原理推导）
  • 命中依赖路由。 在多机部署里，同一个前缀的缓存在哪台机器上，请求就要尽量路由到哪台，否则等于没缓存。这也是为什么有的服务建议带上同一个会话标识。（原理推导）开源引擎里，缓存的 KV 块放在各个推理实例自己的 GPU 显存里，实例之间默认不共享；OpenAI 文档写明，同一组织和区域内对某个模型的路由取决于负载、前缀哈希和 prompt_cache_key，缓存不跨组织、不跨区域复用，而且 prompt_cache_key “影响路由，不会把请求固定到某台机器，也不保证命中”。缓存也不一定只放显存：DeepSeek 的文档写明会落到硬盘，其他厂商放在哪里官方没有公开。

换模型，缓存也会失效。 缓存里存的是 K、V，它们是用模型自己的权重算出来的；换了模型（甚至同一个模型的不同版本），权重不同，同样的 token 算出的 K、V 完全不同，旧缓存对新模型没有意义。（原理推导）官方文档里：OpenAI 把 model 列为会影响缓存前缀的设置，原话是 “A different model can use different weights and caching behavior.”，并说同一组织和区域内的路由是针对某个模型的，但没有写“换模型一定未命中”这句话；Anthropic 我读到的部分没有讲换模型，只写了最小缓存长度因模型而异，以及改 thinking 配置、effort 等设置会让缓存失效。（两家文档我都只逐字读到前面一部分。）所以在同一个会话里中途换模型（比如简单问题切小模型），新模型要把整段前缀重新 Prefill 一遍，反而可能更慢更贵。

不同协议里怎么加缓存

前缀规则对三家都一样，区别只在谁来决定缓存断点：Anthropic 是你来标，OpenAI 默认自动、新模型可以手动标，DeepSeek 完全自动。以下内容核对自三家官方文档（2026-11-24 读取）：Anthropic、OpenAI、DeepSeek。

Anthropic（Claude）OpenAIDeepSeek
怎么开请求顶层加一个 cache_control，或在内容块上加默认自动，不用改请求。GPT-5.6 及以后可用 prompt_cache_options 控制默认开启，不用改代码
缓存多久默认 5 分钟，"ttl": "1h" 为 1 小时GPT-5.6 及以后：30m（默认）或 12h；更早的模型用 prompt_cache_retention（in_memory 或 24h）没有固定时长，用完后“通常几小时到几天内”清理

Anthropic：有两种写法。 第一种最省事，在请求顶层加一个字段，系统自动把断点放在最后一个可缓存的块上：

{
  "model": "claude-opus-5-5",
  "max_tokens": 1024,
  "cache_control": {"type": "ephemeral"},
  "system": "You are an AI assistant tasked with analyzing literary works...",
  "messages": [{"role": "user", "content": "Analyze the major themes."}]
}

第二种是在内容块上自己标断点，缓存到哪一块为止（官方示例：系统提示分两块，把长文档那一块标上）：

"system": [
  {"type": "text", "text": "You are an AI assistant tasked with analyzing legal documents."},
  {"type": "text", "text": "Here is the full text of a complex legal agreement: [...]",
   "cache_control": {"type": "ephemeral"}}
]

“断点”是什么意思？ 它是你在提示词里插的一根“缓存到这里为止”的标记：从开头起，直到并包括标了 cache_control 的那一块，都进缓存；这一块后面的不进。比如请求按顺序是工具、系统提示、一份长文档、用户问题，在“长文档”那一块标断点，前三块一起被缓存，每次都不同的用户问题放在断点后面，不缓存，也不会让前面的缓存失效。顶层写一个 cache_control 是“自动标”，系统把断点放在最后一个可缓存的块上；直接写在某一块上是“自己标”，由你决定缓存到哪一块为止。官方限制是一个请求最多 4 个断点，每个断点最多往前回看 20 个块。多个断点的用处，我的推测是把它们放在不同“变化速度”的分界处（工具表几乎不变、系统提示偶尔变、对话历史每轮增长），这样某一层变了，前面更稳定的缓存还能命中；这一点官方文档没这样讲。

要 1 小时的缓存，写成 "cache_control": {"type": "ephemeral", "ttl": "1h"}。两种写法可以一起用。

cache_control 的意思是“这里可以缓存”；{"type": "ephemeral"} 是缓存的类型，ephemeral 是“短暂的、临时的”，官方文档写的是它目前是唯一支持的类型，默认存活 5 分钟，所以每次都写同一句。放在顶层，是让系统自动把断点放在最后一个可缓存的块上；放在某一块上，是“缓存到这一块为止（包括这一块）”。

Anthropic 的缓存前缀顺序固定为 tools → system → messages，“每一层的改动会让这一层和后面所有层失效”。几条官方写明的细则：

  • 改工具定义：tools、system、messages 全部失效。
  • 改 tool_choice、在任意位置增删图片：messages 失效。
  • 命中要求“100% 一致”，包括所有文本和图片，直到标了断点的那一块。
  • 一个请求最多 4 个断点；每个断点最多往前回看 20 个块，找有没有可命中的缓存。
  • 没到最短长度，即使标了也不缓存，而且不报错，只能看 usage 里的数字才知道。

这几条正好对应前面的“前缀污染”：Anthropic 把“工具放最前、改工具就全断”写进了文档。

OpenAI：默认自动，新模型多了手动选项。 旧模型只要前缀够长就自动缓存；官方建议给共享同一前缀的请求带上稳定的 prompt_cache_key，帮助路由到同一台机器（它影响路由，不保证命中）。GPT-5.6 及以后，可以在 prompt_cache_options 里选 implicit（自动，断点放在最后一条可缓存消息的末尾）或 explicit（自己在内容块上标 prompt_cache_breakpoint），并用 ttl 选 30m 或 12h。官方页上的写法大致如下：

{
  "model": "gpt-6.2-sol",
  "prompt_cache_key": "support:customer_123",
  "prompt_cache_options": { "mode": "explicit", "ttl": "12h" },
  "input": [
    { "role": "developer", "content": [
      { "type": "input_text", "text": "Shared instructions...",
        "prompt_cache_breakpoint": { "mode": "explicit" } } ] },
    { "role": "user", "content": "The user's question..." }
  ]
}

这个例子是我把官方页上分开的几段拼在一起的，字段名都来自官方页面，但官方没有给出完整的合并示例。例子里的 "role": "developer" 是 OpenAI 的角色，不是笔误：官方文本指南写明 developer 消息是应用开发者给的指令，优先级高于 user；Responses API 的角色取值有 user、assistant、system、developer，developer 和 system 都高于 user，我没有找到文档说 developer 取代了 system。官方缓存页也写：想让可复用的指令符合缓存条件，就把它们放在 input 开头的 developer 消息里。另外，GPT-6.2 及以后把顶层 instructions 放在 input 之后，这部分按未缓存价计费，所以别把要缓存的静态内容放在那里。

DeepSeek：不用加任何东西。 官方原话是默认对所有用户开启，不需要改代码。每个请求会在“用户输入末尾”和“模型输出末尾”各留下一个缓存前缀单元，另外还会在检测到的公共前缀和固定 token 间隔处留单元；后一个请求要完整匹配某个前缀单元才命中，而且前缀得已经被写入硬盘缓存，所以文档里的长文档例子是前两个请求都不命中、第三个才命中。官方也明确说是“尽力而为”，不保证 100% 命中。

三家共同的断点原则

判据：断点放在“静态”和“动态”的交界处。

  • Anthropic：断点标在最后一个静态块上（系统提示、工具、固定文档之后），或者用顶层字段让系统自动放在最后一块。
  • OpenAI：prompt_cache_key 对同一类请求保持稳定；用 explicit 时把断点标在静态内容的末尾。
  • DeepSeek：没有断点可标，所以只能靠提示词本身“前面不变”。
  • 无论哪家：上线后看命中数字，别只相信“我写对了”。

实践清单

  1. 静态内容放最前，动态内容放最后。 系统提示词、工具定义、固定文档在前；用户提问、时间戳、会话 ID 在后。
  2. 别在提示词开头写时间、用户 ID、状态。 这是最常见的前缀污染。
  3. 别在对话中途增删工具、改工具顺序。
  4. 历史只追加、不改写。 要压缩历史，就接受压缩那一次的缓存失效，之后再继续追加。
  5. 看命中数再优化。 看接口返回里的缓存命中 token 数（DeepSeek 是 prompt_cache_hit_tokens），数字稳定上涨，才说明吃到了缓存。
  6. 不同厂商机制不同（2026-11-24 价格页）。 Claude 需要在请求里加 cache_control（可以只加一个顶层字段，由系统自动管理断点），5 分钟缓存写入是 1.25 倍、1 小时写入是 2 倍输入价，命中读取 0.05–0.1 倍；OpenAI 价格页单列了缓存写入价（以 Sol 为例，30 分钟 1.25 倍，12 小时 2.5 倍）；DeepSeek 自动识别，不用改代码。

给 10 岁小朋友的版本

  1. 你每天上学，老师都先把同样的开场白讲一遍：“同学们好，今天我们学……”。如果每次都要从头一个字一个字抄，太累了。
  2. 聪明的做法是：第一天抄好，留着。第二天老师说的开头一样，你就直接翻出昨天的笔记。
  3. 但是只要老师的第一个字变了，你就不能直接用了，因为后面每一句都是接着前一句说的。
  4. 笔记本很大，也有不够用的时候：这时候你会把最久没翻过的那几页撕掉，给新的腾地方。
  5. 所以要想省力气，老师（也就是你写的提示词）最好把不会变的话放前面，会变的话放后面。
  6. 每一页笔记也不是一个字一个字存的，而是十几个字一页，页码是用前一页的页码算出来的，一翻就能找到。

回顾

  • 为什么只能是前缀： 一个词的 K、V 取决于它自己和左边所有的词，所以从第一个词开始逐字一致，才能整段复用。
  • 怎么找： vLLM 把提示词分块（典型 16 个 token 一块），每块哈希里带上前一块的哈希，形成哈希链，查表就能找到最长命中前缀；SGLang 则在前缀树上做前缀匹配。
  • 怎么存： 两种办法都让共同前缀只存一份；显存紧张时都按 LRU 淘汰（vLLM 从空闲队列队首，SGLang 从叶子）。
  • 怎么用： 命中的块不做 Prefill，只算未命中的尾巴，省首字延迟，也省输入费用。
  • 怎么写提示词： 静态在前、动态在后，历史只追加，别改工具列表。
  • 边界： 有存活时间、尾块不缓存、按账号隔离、多机要路由。
