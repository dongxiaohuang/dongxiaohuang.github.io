图解 Batch API

TLDR

批处理（Batch API）是把请求一次交给服务商、不等结果，换 50% 的折扣；便宜不是因为模型算得更快，而是因为你同意让服务商挑时间算。

  • 机制：上传一个 JSONL（JSON Lines，每行一个 JSON）文件，创建批次，隔一会儿查状态，完成后下载结果。OpenAI、Anthropic、Gemini 的官方文档都写明按标准价的 50% 计费（2026-11-26 读取）。
  • 代价：延迟上限 24 小时（Gemini 48 小时未完成算过期）；单批上限 OpenAI 5 万请求 / 200 MB，Anthropic 10 万请求 / 256 MB。
  • 为什么便宜（原理推导）：GPU（图形处理器）无论有没有人用都在烧钱，请求量一天里又忽高忽低。批处理把时间的选择权交给服务商，它把活塞进空闲时段。Gemini 文档直接写了“利用机会性的非高峰算力”，DeepSeek 则把同一件事做成分时定价：非高峰价是高峰价的一半。
  • 一笔账：100 万个请求（每个 2,000 token 输入、500 token 输出），Claude Sonnet 5.5 标准价约 $9,000，批处理约 $4,500。
  • LiteLLM：用 OpenAI 格式的 files + batches 接口，同一套代码可以把批次发给 OpenAI、Azure、Vertex、Bedrock、Mistral、vLLM、xAI；它不让批处理更便宜，价格由各家服务商决定。

打开 OpenAI、Anthropic、Gemini 的价格页，都能看到同一个选项：Batch，半价。条件是你不要立刻拿结果，最多等 24 小时。同样的模型、同样的输出，凭什么半价？这篇文章先看各家怎么用、卖多少钱，再解释为什么便宜，最后讲 LiteLLM 怎么把它们接成一套代码。

背景知识：推理时 GPU 要反复读取模型权重，多个请求一起算最划算，见illustrate of vLLM；缓存命中便宜是另一个机制，见illustrate of KV Cache和illustrate of Prefix Caching （前缀缓存）。这篇讲的是第三种省钱方式：用时间换钱。

三家主流 API 都是半价，换来最长 24 小时的等待

让我们先从外部看：对调用者来说，批处理是一个“请求文件进、结果文件出”的接口，中间没有流式输出，也不保证什么时候好。下图是几个模型的官方价格（每百万 token，2026-11-26 读取）。Claude 的批处理价来自 Anthropic 批处理文档的价格表；标准价来自 2026-11-24 的官方价格页（见illustrate of KV Cache的附录）。DeepSeek 没有批处理接口，对应的是官方定价页上的非高峰价。

每个模型两根条：灰色是标准价，蓝色是批处理价（DeepSeek 为非高峰价）。输入和输出各用一个刻度，右边一列是蓝 ÷ 灰。5 个模型全是 0.5×。

数字都一样：输入、输出一起减半。再看各家的规则差别：

厂商折扣等待上限单批上限结果保留 / 过期
OpenAI标准价的 50%24 小时（completion_window 目前只能填 24h）5 万个请求，输入文件 200 MB输出文件默认保留 30 天；到期未完成的请求被取消，已完成的照常计费
Anthropic（Message Batches）标准价的 50%24 小时，官方说多数 1 小时内完成10 万个请求或 256 MB，先到者为准结果保留 29 天；24 小时内没跑完则过期

Amazon Bedrock部分模型比按需价低 50%本次未核实本次未核实—
DeepSeek没有批处理接口；非高峰价是高峰价的一半（同步调用）无——

这张表背后其实是三种形态，都在出售同一样东西：时间上的弹性。

  • 异步批处理（OpenAI、Anthropic、Gemini Batch、Bedrock）：文件进、文件出，半价，等最长 24 小时。
  • 同步低优先级：Gemini Flex 也是半价，但仍是普通同步调用，目标延迟 1–15 分钟，流量高峰时可能被抢占（官方称 sheddable）。适合“下一步依赖上一步输出”的 Agent 链，批处理做不到这一点。
  • 分时定价（DeepSeek）：同步调用，高峰时段（周一至周五 UTC 01:00–04:00 和 06:00–10:00，中国法定节假日除外）收全价，其余时间半价。

实际要等多久？官方只给上限。Anthropic 写“多数批次在 1 小时内完成”；OpenRouter 自己的批处理测试版（不是 OpenAI 的数据，我只读到摘要）说中位数 7 分钟、90% 在 1 小时内，见其博客。24 小时是上限，不是典型值，但你无法要求它更快。

一个批次只有五步：不占连接，靠 custom_id 对号取结果

五步流程在各家基本一致，下图以 OpenAI 的格式为例（LiteLLM 也沿用它）。点 Next step 一步步看。

五步：写文件、上传、建批次、排队、下载。只有第 4 步需要“等”，而且等的时候你不占着任何连接。

注意两个细节。 第一，输出文件里的结果不保证按输入顺序，必须用你自己写的 custom_id 对号。第二，批次里单个请求可以失败，其他的照常完成：OpenAI 会把失败的写进单独的错误文件，Anthropic 在每条结果里标明成功、报错、取消或过期。所以重试要按 custom_id 挑出失败的那几条重新提交，不用整批重来。

便宜的原因：GPU 的成本固定，批处理让服务商把活放进空闲时段

（以下是原理推导。厂商没有公布内部成本，官方文档只给出价格和规则。）

示意图：一天里实时请求（灰）忽高忽低，GPU 容量（红虚线）是固定的；蓝色是空出来的容量，批处理可以填进去。琥珀色竖带是 DeepSeek 官方标出的高峰时段。灰色曲线的形状是我画的示意，不是真实流量。

第一，GPU 的成本是固定的。 机器买了或租了，不管有没有请求都在花钱。成本公式里分母是“这块卡一天实际算了多少 token”，所以空转是纯浪费，填满一点，每个 token 的成本就低一点。

第二，实时流量一天里起伏很大，容量必须按高峰配。上图灰色以下是实时请求，蓝色是谷底的空档。DeepSeek 把高峰时段写进了定价页（UTC 01:00–04:00、06:00–10:00，换算成北京时间是 09:00–12:00 和 14:00–18:00，正好是上班时间），非高峰半价；这等于把“谷底更便宜”直接标在了价目表上。Gemini 文档对 Flex 的解释也是同一句话：利用“机会性的、非高峰的算力”。

第三，批处理给了服务商挑时间的自由。 实时请求要在几秒内开始吐字，不能等；批处理请求可以排队，等空档来了再算。服务商的收益是：谷底也有活干。你的成本是：不知道具体什么时候好。

第四，批量更利于 GPU 的算力利用。 解码阶段每一步都要把几十 GB 权重读一遍，多个请求一起算几乎不多花时间（原理见illustrate of vLLM）。批处理没有首字延迟要求，调度器可以放心把一步里的并发数堆到上限；它还可以把前缀相同的请求排在一起，复用 KV Cache。Anthropic 的文档就建议：批次可能跑过 5 分钟，所以配合 1 小时缓存时长使用，缓存命中率更高。

第五，批处理可以被打断和重试。 Gemini 把批处理描述为“可被抢占（sheddable）、但有 24 小时的自动重试和排队系统”。也就是说，实时流量一来，批处理的算力可以先让出去，之后再补算。

为什么各家都是恰好 50%？

判断标准：这个折扣是成本公式算出来的，还是定价决策？

  • 像是定价决策：三家文档都写“50%”，输入输出一刀切，不随模型变（本表里 5 个模型全是 0.5×）。如果是成本公式，不同模型、不同输入输出比例应该各不相同。（原理推导）
  • 但方向是真实的成本差：非高峰、可排队、可抢占的算力，成本确实比实时低；50% 是服务商把一部分省下的钱让给你，同时用折扣把非紧急流量引到谷底。
  • 所以不要期待它继续降：它的上限由“谷底有多少空算力”决定，不是越便宜越好。

算一笔账：100 万个请求，Sonnet 5.5 从 9,000 美元降到 4,500 美元

假设每个请求 2,000 个输入 token、500 个输出 token，共 100 万个请求。Claude Sonnet 5.5 标准价是 $2 / $10（每百万输入 / 输出 token），批处理价是 $1 / $5。

输入输出合计
token 总量2,000 MTok（20 亿）500 MTok（5 亿）—
标准价2,000 × $2 = $4,000500 × $10 = $5,000$9,000
批处理价2,000 × $1 = $2,000500 × $5 = $2,500$4,500

（MTok 是百万 token。）100 万个请求超过 Anthropic 单批 10 万的上限，所以要拆成至少 10 个批次。这笔账的假设：输出长度和输入长度都是估计值，真实账单看接口返回的 usage。如果几十万个请求共享一段很长的系统提示词，还可以叠加提示词缓存；官方文档建议用 1 小时缓存，具体叠加多少折扣以各家价格页为准（我没有逐家核对）。

LiteLLM 把各家批处理统一成 OpenAI 的 files + batches 接口

LiteLLM 是一个开源 Python 库加代理服务（Proxy）。对批处理，它做两件事：接口统一（你写一次 OpenAI 格式的代码）和路由（按配置发到不同厂商）。它不会让批处理更便宜，折扣来自厂商。

按 2026-11-26 的 LiteLLM 批处理文档，支持批处理的服务商有：OpenAI、Azure、Vertex AI、Amazon Bedrock、Mistral、vLLM、xAI。这个列表里没有直接的 Anthropic，想用 Claude 的批处理，要么走 Bedrock 或 Vertex，要么直接用 Anthropic 自己的 SDK（软件开发包）。

LiteLLM Proxy 站在你的代码和各家服务商之间：校验文件、发放托管文件 id、选部署、检查归属。

用法一：直接在 Python 里用（SDK）。 先上传文件，再创建批次，轮询，最后下载。下面照搬官方文档里的 OpenAI 示例，把函数名对上就行。

import litellm, asyncio, os
os.environ["OPENAI_API_KEY"] = "sk-..."

async def main():
    # 1. 上传 mydata.jsonl（每行一个请求，格式见上文第 1 步）
    f = await litellm.acreate_file(
        file=open("mydata.jsonl", "rb"),
        purpose="batch",
        custom_llm_provider="openai",
    )
    # 2. 创建批次
    b = await litellm.acreate_batch(
        completion_window="24h",
        endpoint="/v1/chat/completions",
        input_file_id=f.id,
        custom_llm_provider="openai",
    )
    # 3. 轮询，直到进入终态（completed / failed / expired / cancelled）
    while True:
        b = await litellm.aretrieve_batch(batch_id=b.id, custom_llm_provider="openai")
        if b.status in ("completed", "failed", "expired", "cancelled"):
            break
        await asyncio.sleep(30)   # 批处理以分钟计，不要 5 秒轮询一次
    # 4. 下载结果（输出文件 id 在 completed 的批次上）
    out = await litellm.afile_content(file_id=b.output_file_id, custom_llm_provider="openai")
    print(out.text)

asyncio.run(main())

用法二：启动 LiteLLM Proxy，用任意 OpenAI SDK 调用。 适合多人、多服务共用一套密钥和限额。最小配置（来自官方文档）：

model_list:
  - model_name: gpt-6.1-sol
    litellm_params:
      model: openai/gpt-6.1-sol
      api_key: os.environ/OPENAI_API_KEY

files_settings:
  - custom_llm_provider: openai
    api_key: os.environ/OPENAI_API_KEY

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
litellm --config config.yaml      # RUNNING on http://0.0.0.0:4000

然后客户端把 base_url 指向代理，其他和直接调 OpenAI 完全一样：

from openai import OpenAI
client = OpenAI(base_url="http://0.0.0.0:4000", api_key="sk-<your-litellm-key>")

f = client.files.create(file=open("request.jsonl", "rb"), purpose="batch")
b = client.batches.create(input_file_id=f.id, endpoint="/v1/chat/completions",
                          completion_window="24h")
# 之后 client.batches.retrieve(b.id) 轮询，client.files.content(b.output_file_id) 下载

用法三：托管文件（Managed Files）：一个模型名、多个部署、负载均衡。 把同一个批处理模型名配到多个部署上，并声明 mode: batch。上传文件时用 target_model_names 指定，文件会被写到所有匹配的部署，批次会在它们之间做负载均衡。来自 Managed Files 文档（该功能标注为 BETA，SDK 不支持，需要 Postgres 存文件 id）：

model_list:
  - model_name: "gpt-5.4-mini-batch"
    litellm_params:
      model: azure/gpt-5.4-mini-general-deployment
      api_base: os.environ/AZURE_API_BASE
      api_key: os.environ/AZURE_API_KEY
    model_info:
      mode: batch          # 标记这是批处理模型

  - model_name: "gpt-5.4-mini-batch"
    litellm_params:
      model: openai/gpt-5.4-mini
      api_key: os.environ/OPENAI_API_KEY
    model_info:
      mode: batch
f = client.files.create(
    file=open("request.jsonl", "rb"), purpose="batch",
    extra_body={"target_model_names": "gpt-5.4-mini-batch"},   # 必须和 jsonl 里的 model 一致
)
b = client.batches.create(input_file_id=f.id, endpoint="/v1/chat/completions",
                          completion_window="24h")

几个容易踩的点（均来自上面两份官方文档）：

  • request.jsonl 里的 model 要用代理里的模型名；在托管文件模式下，必须是 mode: batch 的模型名，并与上传时的 target_model_names 一致。
  • 限额：LiteLLM 默认在提交前读一遍输入文件，把 token 数和请求数记入调用者的 TPM / RPM（每分钟 token 数 / 请求数）限额，大文件会增加延迟。配置里可以关掉：disable_batch_input_file_rate_limiting: true。
  • 归属检查：每个批次和文件属于创建它的 key、用户、团队；别的团队的 key 访问会得到 403。
  • 成本追踪：文档的功能表写着“Cost Tracking：LiteLLM Enterprise only”，开源版不一定有这一项，我没有实际验证。
  • 取消：client.batches.cancel(batch.id)，状态先变 cancelling，再变 cancelled。

只有“不急”的任务才值得用批处理，Agent 的在线链路不行

  1. 适合：离线评测、数据标注、给大量文档做摘要或打标签、批量生成嵌入、夜间报表。共同点：结果晚几小时没人在意，请求之间互相独立。
  2. 不适合：用户在等的聊天；“第 N+1 次调用依赖第 N 次输出”的 Agent 循环。后者每一步都要排队，一条 10 步的链路最坏要等 10 个批次周期。这种场景看 Gemini Flex 或 DeepSeek 非高峰价这类同步低价档。
  3. 先小后大：先用 10 条请求跑通整条流程，确认 custom_id、输出解析、错误文件处理都对，再放量。
  4. 按批次上限拆分：OpenAI 5 万 / 200 MB，Anthropic 10 万 / 256 MB，Gemini 文件 2 GB。LiteLLM 文档里还列了 Vertex（200,000 条 / 1 GB）和 Bedrock（1 GB 每文件）的上限，路由到哪家就按最小的拆。
  5. 共享前缀放最前面：整批都用同一段系统提示词时，保持它一字不差，缓存才可能命中（见illustrate of Prefix Caching （前缀缓存））。
  6. 给过期留余地：OpenAI 超时的批次会取消未完成的请求，已完成的照常计费；Anthropic 24 小时没跑完也会过期。设计成“只重提交失败的那几条”。

给 10 岁小朋友的版本

  1. 餐厅有两种点餐。 现点现做要马上上菜，厨师得随时待命；“预订外卖，明天来取”可以等厨师不忙的时候做。
  2. 不忙的时候厨房也在花钱。 灶台、厨师工资不会因为没客人就少掉，所以厨师很愿意在空闲时多做几份。
  3. 所以预订外卖打五折。 不是菜更便宜，是你让厨师自己挑时间。AI 公司的 Batch 就是这样。
  4. 要给每份餐写个编号。 外卖不一定按你下单的顺序做好，编号（custom_id）才知道哪份是哪份。
  5. LiteLLM 是总机。 你只对着一个电话说话，它帮你转给不同的餐厅；但它不会替餐厅打折。

回顾

  • 形态：异步批处理（OpenAI、Anthropic、Gemini、Bedrock）、同步低优先级（Gemini Flex）、分时定价（DeepSeek），都是卖时间弹性，几乎都是半价。
  • 流程：JSONL → 上传 → 建批次 → 排队 → 下载；结果无序，靠 custom_id 对号；24 小时是上限。
  • 原理（推导）：固定成本的 GPU 一天里有空档，批处理让服务商把活塞进去，并且可以排序、合并、抢占。50% 是定价决策，方向有成本依据。
  • LiteLLM：统一接口 + 路由，不改变价格；直接的 Anthropic 不在它的批处理支持列表里。
